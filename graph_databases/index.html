Graph databases,
without the hype.

What a graph database actually is, why "do I need a graph DB?" is almost always the wrong question, where the relationships genuinely earn a graph engine, and the specific conditions under which a dedicated graph database is the correct answer. Every claim below is dated, versioned, and sourced; vendor benchmarks are labeled as vendor claims.

4 parts · decision matrix · worked SQL + Cypher · sources with access dates

Verdicts up front
  1. The honest default is: use the relational database you already have. If your data lives in PostgreSQL and your traversals are one to three hops over indexed columns, foreign keys plus a well-chosen index (or a recursive CTE) already give you a graph — exact, transactional, explainable — before you add anything.
  2. A graph database is an OLTP-traversal tool, and its edge is depth × fan-out, not "connections". Index-free adjacency makes each hop roughly O(1) in a native engine, so cost tracks a node's degree, not the table size. That advantage only appears when queries walk many hops or branch widely; a two-hop JOIN does not feel it.
  3. PostgreSQL gives you a ladder, not a fork. Recursive CTEs → ltree / pgRouting → Apache AGE (openCypher in the same tables) →, from the SQL:2023 line, SQL/PGQ. You climb it one rung at a time; you almost never have to "migrate to a graph database".
  4. Dedicated graph databases are justified by specific, checkable conditions — deep traversal at high concurrency, whole-graph analytics as a product feature, graph-native write patterns, or hard isolation from the OLTP system — not by the phrase "our data is connected".
  5. The vendor benchmark layer here is worse than in vector search — treat every number as a marketing artifact until you reproduce it. TigerGraph's "2×–8000×", Memgraph's "41× lower latency", ArcadeDB's "LDBC leader" are all self-published on self-chosen setups. Run LDBC SNB/Graphalytics, or your own workload, on your data.

Data is in Postgres; queries are 1–3 hops over foreign keys with a filter (org charts, comments, tag graphs, BOM) Postgres JOINs, indexed Exact, transactional, explainable, already operational. A graph DB adds a second source of truth to buy a speed you don't need.
Variable-depth hierarchies / transitive closure on your own tables (category trees, permission rollups) WITH RECURSIVE or ltree Native, no extension, 100% exact. UNION (not UNION ALL) gives you cycle detection for free.
You want Cypher-style pattern matching and a property-graph model, data already in Postgres, deep-ish traversals at moderate scale Postgres + Apache AGE (1.8.x) One system: ACID, joins across SQL and Cypher, RLS, backups come free. You want standard SQL graph syntax over existing tables, and can wait SQL/PGQ — but not in GA yet (as of Oct 2026) CREATE PROPERTY GRAPH/GRAPH_TABLE reached PG 19 beta and was reverted 2026-09-07; the Nov 2026 GA ships without it. Plan for v20.
Deep traversal (many hops / wide fan-out) at high concurrent QPS, as the product's core path Native graph DB (Neo4j, Memgraph, TigerGraph…) Index-free adjacency makes depth cheap; the OLTP engines optimize exactly this. Measure your own hop profile first.
Whole-graph analytics (PageRank, communities, connected components) as a feature Graph analytics platform (Neo4j GDS, TigerGraph, Neptune Analytics) or in-process (NetworkX, Graph-tool) OLAP over the whole graph is a different problem from OLTP traversal; a transactional store is rarely the right place to run it.
Retrieval for an LLM that must reason over relationships (GraphRAG) Graph (often + vectors) — Neo4j graphrag, LlamaIndex, Microsoft GraphRAG, LightRAG Explicit relationships give multi-hop context and explainability similarity search can't. Indexing cost is 10–1000× basic RAG; use it where aggregation is the point.
Billions of relationships, petabyte scale, distributed compute mandatory Distributed MPP graph (TigerGraph, NebulaGraph, GraphScope) Single-machine native stores hit memory/hop walls here; sharded MPP keeps latency stable at depth (vendor claim — verify).

Reading graph benchmarks honestly

The graph-database benchmark layer is dominated by vendors benchmarking themselves. Example: ArcadeDB's widely-shared LDBC Graphalytics table (PageRank 0.48 s vs "Neo4j 2026" 11.15 s) is published on ArcadeDB's own site, run on ArcadeDB's chosen setup, with "Neo4j 2026" left unspecified; Memgraph's "41× lower latency" uses a self-run whitepaper; TigerGraph's "2×–8000×" is a 2018-era report that's still in circulation. Directionally, they say "architecture and depth matter"; none of them is a constant you can deploy on. Reproduce on your graph — LDBC SNB for pattern matching, LDBC Graphalytics for analytics — before you choose an engine on a number.

Scope and method

This is an engineering investigation, not a product review. Research window: October 2026. Primary sources checked directly: the Apache AGE README, release notes and FAQ (v1.8.0); PostgreSQL 19 release notes and the docs/19 Property Graph / Graph Query sections (and the mailing-list revert threads for SQL/PGQ); the pgRouting 4.0 manual; ISO catalog entries for GQL (ISO/IEC 39075) and SQL/PGQ (ISO/IEC 9075-16); Neo4j Cypher/GQL-conformance docs and 2026 release notes; and the Kuzu archival notice plus fork lineage. Secondary sources are blog- and vendor-grade and are cited as such.

It sits alongside this repository's vector_databases/ report. Where that report argued "vectors are columns; use Postgres first," this one argues the same for relationships: edges are foreign keys, and a graph is a query shape — not necessarily a second database. The two meet in GraphRAG (Part 3 §3), where graph retrieval and vector retrieval are the same retrieval problem from two ends.
