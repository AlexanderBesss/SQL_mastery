Part 3 of 4 · Where graphs earn their keep

Eight use cases
that survive scrutiny.

Each entry states the signal that it's genuinely a graph problem, the recipe (usually in Postgres, sometimes a dedicated engine), the strict caveat, and the bail-out condition — the point at which the honest answer stops being "make it a graph". Read the bail-outs as part of the use case.

The admission test — run every idea through it
  1. Can you name the query that chains relationships — and how deep and wide it goes? "Friends of friends who share a device with a sanctioned entity" is graph-shaped; "this customer's orders" is a foreign key. If you can't state hop depth and fan-out, you can't justify a graph engine.
  2. Is the relationship itself a domain fact with properties and time (who transferred what to whom, when, how much)? If relationships are just foreign keys between typed records, relational modeling is not a compromise — it's the right answer.
  3. Is traversal on the critical path at concurrency (OLTP), or is the work whole-graph computation (OLAP)? The two answer sets are different engines. All eight cases below pass at least one test in Postgres itself — which is the point.

1 · Fraud rings, AML, and fraud-network detection

Signal: the fraud is in the shape — mule chains, ring topologies, accounts sharing devices/addresses/payment instruments, circular transfers. Why graphs: "find accounts within 3 transfers of a confirmed mule that share a device with ≥2 flagged accounts" is a bounded-depth pattern match; in SQL it's a join pile-up nobody maintains.

-- Apache AGE: shape detection (Postgres stays the system of record)
SELECT * FROM cypher('fraud', $$
  MATCH (s:Suspect)-[:TRANSFERS_TO*1..3]->(a:Account)
  WHERE NOT a.flagged
  WITH a WHERE size([(a)<-[:USES_DEVICE]-(o:Account)-[:USES_DEVICE]->(b:Account)
                     WHERE b <> a | collect(b)]) >= 2
  RETURN a.id
$$) AS (id agtype);

Strict caveats: batch risk-scoring algorithms (PageRank-style money flow, community detection) are OLAP — run them off the request path (GDS-class tools, or extract edges to graph-tool / NetworkX / Spark GraphFrames). Thresholds and features need labeled outcomes or you're shipping noise. Supernodes (shared Wi-Fi in an apartment block, payment intermediaries) dominate latency and false positives; model them out of the traversal.

Bail-out: single-account rules ("velocity > X") — that's a feature on a row, do it in SQL. Graphs enter when cross-account structure carries the signal.

2 · Knowledge graphs and GraphRAG

Signal: an LLM (or a human) must answer multi-hop questions over your corpus: "which supplier risks affect the product family owned by this account?" Vector RAG returns similar chunks; the graph returns the path between entities, with provenance. The 2024–2026 pattern stack: Microsoft GraphRAG (extract entities/relations with an LLM at index time, Leiden community detection, hierarchical summaries), Neo4j's neo4j-graphrag pipeline + Text2Cypher, LlamaIndex PropertyGraphIndex, cheaper variants (LightRAG, Nano-GraphRAG).

Hype check — where graph and vector reports meet

GraphRAG's indexing cost is the honest headline: community write-ups put LLM extraction + summarization at ~10–1000× basic-RAG embedding cost per chunk ($0.01–0.10/chunk vs ~$0.0001), plus a graph store to operate. The retrieval-quality win concentrates in aggregation and multi-hop questions; for "what does the policy say about X", hybrid vector+FTS RAG already works. Route to the graph when the question needs the path, not the passage. (This is the same conclusion the vector report reached from the other side: retrieval is a pipeline, not a product.)

Strict caveats: LLM-extracted graphs are noisy — entity dedup, relation typing, and schema enforcement (enforce_schema / SHACL on RDF) are the hard 80% of the work. Keep source chunk provenance on every edge or you've built a hallucination amplifier with nice visuals.

Bail-out: flat corpora, single-hop lookups — the vector-databases report covers it; don't bolt a knowledge graph onto retrieval that never composes.

3 · Recommendations and co-occurrence ("also bought", "also viewed")

Signal: "customers who bought this also bought…" — the graph is (p1)-[:PURCHASED_WITH {count, window}]->(p2), built offline from baskets. Graph form makes constraints cheap: filter by margin, stock, and category in the same pattern.

-- Postgres materializes the edge table; traversal is an index hit
WITH co AS (
  SELECT b.product_id AS rec, count(*) AS strength
  FROM   order_items a
  JOIN   order_items b ON a.order_id = b.order_id AND a.product_id <> b.product_id
  WHERE  a.product_id = :product AND a.ordered_at > now() - interval '90 days'
  GROUP  BY 1 ORDER BY strength DESC LIMIT 20
)
SELECT p.* FROM co JOIN products p USING (product_id)
WHERE  p.in_stock IS TRUE ORDER BY strength DESC LIMIT 8;

Strict caveats: this is a two-hop pattern — a precomputed co-occurrence table (edge list) usually beats a live graph engine; that's fine, it is the graph. Popularity bias and catalog drift need windowing/decayed counts. A graph DB earns its place when recommendations must chain ("similar items from the brand this customer's team prefers"), not for the base pair scoring.

Bail-out: once behavioral data is rich, trained embeddings / two-tower models usually beat hand-built edge graphs (see the vector report, Part 3 §3).

4 · Access control, permissions, and reachability

Signal: permissions that inherit and delegate: groups contain groups, folders contain folders, shares propagate, service accounts act for users. "Can identity X reach resource Y, through which chain?" is a graph reachability question — and the answer must be explainable in an audit.

Recipe: the guarded recursive walk from Part 2 §2 is exactly this query — swap manager_id for (grantee, grants_to) edges, keep the chain[] array, and it doubles as the audit trail: "X reached Y because group A contains group B which holds role R". For read-heavy authorization, precompute a closure table (every reachable pair, materialized) or use ltree — write-time cost for read-time certainty.

Strict caveats: this is the highest-blast-radius use case on the list: a cycle bug in grant propagation is a security incident. Enforce acyclicity at write time (path arrays, closure tables, or ltree), test with adversarial fixtures, and cap depth. Zanzibar-style systems (Google, then open-source implementations) deliberately use narrow lookups with caching instead of unbounded traversal — a graph model yes, but not a graph database on the request path.

Bail-out: static RBAC tables (≤2 joins, no delegation chains) — SQL, and RLS is already your enforcement layer.

5 · Network/IT impact analysis, blast radius, attack paths

Signal: CMDBs, cloud inventories, and security graphs ask "what breaks if this service dies?" and "what path leads from this laptop to the crown-jewel database?" Multi-hop dependencies (hosts→VMs→clusters→apps→business services) are exactly what joins tangle into and graph traversals express directly. Attack-path tooling (BloodHound-class) is graph analytics in the literal sense.

-- AGE: dependency descendants of a failing node
SELECT * FROM cypher('cmdb', $$
  MATCH (n:Service {id: 'payments-api'})<-[:DEPENDS_ON*1..4]-(impacted)
  RETURN DISTINCT impacted.id, impacted.tier
$$) AS (id agtype, tier agtype);

Strict caveats: dependency graphs rot — stale edges give confidently wrong blast radii; ingestion from IaC/cloud APIs must be automated and timestamped (put observed_at on every edge). Deep transitive dependency walks over cyclic infra graphs need the VLE discipline from Part 2 §7.

Bail-out: a fixed 1–2-level dependency list — a JSONB column plus an index answers it, and honestly.

6 · Entity resolution, master data, customer 360

Signal: the same real-world entity appears as many records (emails, phones, addresses, company IDs) and you must merge/survive them: "everything we know about this person/company". Identity resolution naturally forms islands of linked records — connected components are the unit of work, and merges are graph surgery (redirect edges, merge nodes, keep provenance).

Recipe: blocking keys + match rules produce candidate edges (SQL with pg_trgm/btree_gin), a components pass clusters them (pgRouting's component functions, NetworkX offline, or GDS at scale), survivorship rules pick the master record. Keep every match edge with score and rule id — an audit will ask "why are these two the same entity?".

Strict caveats: false merges are worse than duplicates (data crosses customers — think privacy); threshold your match scores on labeled pairs, review big clusters first. The graph is a layer: the master record stays relational.

Bail-out: exact business keys already exist across systems (same tax ID is the join key) — that's MDM with a join, not entity resolution.

7 · Lineage and dependency graphs (data, code, supply chain)

Signal: "if I change this column / table / part / function, what breaks?" — lineage (dbt/ODPS-style column lineage), code dependency graphs, BOMs, supply-chain tier-N risk. Nodes with types, edges with kind and time, questions in both directions (what do I affect? what affects me?).

Recipe: an (src, dst, kind, observed_at) edge table is the whole substrate; impact queries are the Part 2 §2 recursive walk with the path kept; graph visualization (Cytoscape-style) is where the payoff shows. The Kuzu-lineage tooling (codespine's blast-radius work over a code graph) is a good embedded-engine case study of the pattern.

Strict caveats: lineage graphs are only as good as their harvest — manual entry dies in a quarter. Generated-at-build-time ingestion is the feature; the graph is the report. Depth limits and per-type edge filters are non-negotiable on dense call graphs.

Bail-out: trees you always read top-down — ltree or adjacency + recursive CTE; a graph database adds nothing to a tree.

8 · Routing, catchments, and logistics (the graph you already own)

Signal: roads, cables, pipes, flight legs, delivery legs — weighted networks with shortest-path, driving-distance, and k-shortest-path questions. This is graph OLTP/OLAP in the literal, original sense.

SELECT * FROM pgr_drivingDistance(
  $$SELECT id, source, target, cost, reverse_cost FROM road_edges$$,
  :start_vertex, 30.0 /* minutes */, directed => true, reverse => false);
-- then join the reachable vertex set to your POI/facility tables in plain SQL

Strict caveats: pgrRouting assumes your edge table is a clean network (no dangling nodes, correct direction semantics, turn restrictions via pgr_trsp); network prep is most of the project. Large national-scale routing wants pre-processing (contraction hierarchies in dedicated routing engines like Valhalla/OSRM) — pgRouting is the right answer at city/utility scale, not continental-scale ride-hailing.

Bail-out: you only need geodesic distance, not paths — that's PostGIS, not graphs.
