Part 2 of 4 · The PostgreSQL case

Relationships are foreign keys.
Graphs are query shapes.

Before a second database enters the picture, PostgreSQL already gives you a ladder of graph capability: indexed joins, recursive CTEs, ltree, pgRouting, Apache AGE's openCypher over the same heap and WAL, and a standard-SQL destination (SQL/PGQ) that the project is slowly walking toward. This page is the strict engineering manual: what each rung guarantees, what it costs, where the real ceilings are.

1 · The ladder: five rungs before a second database

RungYou reach it whenTool
1Hops are fixed at 1–3 and filters are typedPlain indexed JOINs (already have it)
2Depth is variable, but data is in your tablesWITH RECURSIVE
3Hierarchy is the domain (trees, taxonomies, org charts)ltree (core since forever) or closure tables
4Network algorithms over SQL tables (routing, reachability costs)pgRouting 4.0
5You want a graph model and Cypher, still inside PostgresApache AGE 1.8.x (+ its own algorithms-lite SRFs)

Each rung keeps the same properties you already pay for: ACID, WAL, replicas, PITR, pg_dump, RLS, constraints. The only reason to leave the ladder is a measured wall: deep traversal latency at concurrency, or whole-graph analytics as a product (Parts 3–4).

2 · The baseline: indexed joins + recursive CTEs

-- Variable-depth tree walk, with cycle guard via UNION (implicit dedup)
WITH RECURSIVE org_path AS (
    SELECT id, name, manager_id, 1 AS depth, ARRAY[id] AS seen
    FROM   employees
    WHERE  id = :root
    UNION                                  -- UNION, not UNION ALL: dedup = cycle detection
    SELECT e.id, e.name, e.manager_id, p.depth + 1, p.seen || e.id
    FROM   employees e
    JOIN   org_path p ON e.manager_id = p.id
    WHERE  p.depth < 20                    -- belt-and-braces depth cap
)
SELECT * FROM org_path ORDER BY seen;      -- 'seen' doubles as the path
The two decisions that decide recursive-CTE performance
  1. Index the traversal predicate. CREATE INDEX ON employees (manager_id); — without it every level is a sequential scan and the "graph" is O(depth × rows).
  2. Choose dedup semantics deliberately. UNION ALL is faster but infinite-loops on cycles; UNION dedups rows (cost: sorting/hashing per level); an explicit seen[] array (or Postgres 18-style cycle columns) gives you path semantics. openCypher uses edge-unique path semantics — neither SQL default matches it exactly.

This pattern — indexed FK + recursive CTE — is a genuinely working graph store for hierarchies, reachability, and small-world neighborhoods up to tens of millions of edges, with 100% exactness and a query plan you can read. It is also the fallback the PostgreSQL release team itself recommends after pulling SQL/PGQ from v19 ("Recursive CTEs, or a graph extension such as Apache AGE").

3 · Adjacent rungs: ltree and pgRouting

ltree (core module) stores hierarchy paths as labels (electronics.tv.lcd) and indexes them with GiST/GIN: ancestor/descendant queries (@>, <@, lquery patterns) become index lookups instead of walks. For trees-and-subtrees workloads it beats recursive CTEs on read-heavy access patterns; maintenance is path rewrites on reparenting.

pgRouting 4.0 implements the classic network-algorithm family as SQL functions over ordinary edge tables: pgr_dijkstra, pgr_aStar, pgr_drivingDistance, pgr_KSP (k-shortest), TSP families, turn-restricted routing (TRSP), plus connected-components style helpers. The signature pattern feeds it a SELECT of (id, source, target, cost [, reverse_cost]):

SELECT seq, node, edge, cost, agg_cost
FROM   pgr_dijkstra($$SELECT id, source, target, length_m AS cost
                     FROM   road_edges$$, :from_v, :to_v, directed => false);

Pair it with PostGIS and you have road-network routing, catchment areas, and utility-network analysis — graph work done by a 4.0-version, Boost-backed extension, with no graph database anywhere.

4 · Apache AGE: status, licensing, guarantees

  • Current release: AGE 1.8.0 (ASF catalog 2026-08-06; EDB packaging 2026-08-11). Supports PostgreSQL 11–18 — master branch targets PG 18; PG 12–17 release branches exist. Docker images, source builds, EDB's packaged extension; also runs on stock managed Postgres where operators enable it.
  • License: Apache 2.0, Apache Software Foundation top-level project (since May 2022) — permissive, governance-stable, no single-vendor capture.
  • Full Postgres semantics: graph operations run on Postgres' transaction/cache and storage layers — ACID (the FAQ confirms ACID across graph, relational, and JSON document), MVCC, WAL, replication, backups, triggers, constraints on label tables, and RLS support since 1.7.0 (Jan 2026).
  • Hybrid querying is the core promise: cypher() is a table function, so Cypher and SQL compose in one statement and one transaction — the property dedicated graph stores keep charging you to rebuild via sync.
  • Scale ceiling: 281,474,976,710,655 (2⁴⁸−1) combined vertices + edges per graph (graphid is label(16 bits) + entry(48 bits)); many graphs per database.
  • Feature surface (1.8.x): openCypher subset (MATCH/CREATE/MERGE with ON CREATE/ON MATCH SET since 1.8, OPTIONAL MATCH, UNWIND, WITH, ORDER/LIMIT, aggregates, list predicates all()/any()/none()/single(), reduce()); variable-length paths with major 1.8 VLE performance work; shortest_path()/all_shortest_paths() set-returning functions and create_subgraph() added in 1.8; agtype ↔ jsonb casts; index-scan support; CSV graph loaders; python/java/node/rust/.net drivers.

5 · Under AGE: label tables, graphid, agtype, indexes

AGE is transparent on purpose: create_graph('social') makes a schema with _ag_label_vertex and _ag_label_edge parent tables; every label you use (:Person, :KNOWS) becomes its own child heap table:

social."Person"   (id graphid PK, properties agtype NOT NULL DEFAULT agtype_build_map())
social."KNOWS"    (id graphid PK, start_id graphid, end_id graphid,
                   properties agtype NOT NULL DEFAULT agtype_build_map())

Consequences worth internalizing:

  • You can query the graph in plain SQL. SELECT * FROM social."KNOWS" WHERE start_id = ... works; properties::jsonb is a documented cast in 1.8. The graph is ordinary tables — autovacuum, replicas, pg_stat_statements, FDW tricks all apply.
  • Indexes are Postgres indexes. The FAQ is explicit: AGE "uses PostgreSQL's indexes" and agtype behaves JSONB-like, so B-tree/Hash/GIN apply. The workhorse is a GIN with the containment opclass so MATCH (p:Person {name:'Ada'}) starts from an index, not a scan:
-- property lookup for the pattern start (see AGE manual for the current opclass name)
CREATE INDEX ON social."Person" USING gin (properties agtype_properties_ops);
-- 1.7.0 added indexes on id columns (endpoint joins, VLE lookups):
CREATE INDEX ON social."KNOWS" (start_id);
CREATE INDEX ON social."KNOWS" (end_id);
The disclosed tradeoff

Because edges are heap rows joined by graphid, AGE is a non-native graph layer (Part 1 §5): its own FAQ says "AGE uses relational models under the hood. Some limitations of the relational model apply to AGE, for example large amounts of table joins." AGE counters with custom scan nodes and the 1.8 VLE overhaul (hash-adjacency structure + flat edge arrays), but the honest expectation is: shallow pattern matching ≈ index cost; deep fan-out ≈ join cost. Benchmark your hop profile; don't assume O(1)-per-hop.

6 · Cypher in AGE: shapes, MERGE, and the sharp edges

CREATE EXTENSION age;
LOAD 'age';                                    -- 1.8 can instead go in shared_preload_libraries
SET search_path = ag_catalog, "$user", public; -- per session, like always

SELECT create_graph('fraud');

-- create nodes / typed edges
SELECT * FROM cypher('fraud', $$
  CREATE (a:Account {id: 1001, risk: 'new'})-[e:TRANSFERS_TO {amount: 2500, at: '2026-10-12'}]->(b:Account {id: 2002})
$$) AS (v agtype);

-- pattern match: the canonical 2-hop ring probe
SELECT * FROM cypher('fraud', $$
  MATCH (a:Account {id: 1001})-[:TRANSFERS_TO]->(m:Account)-[:TRANSFERS_TO]->(b:Account {id: 1001})
  RETURN m
$$) AS (m agtype);

-- idempotent upsert (ON CREATE/ON MATCH SET arrived in 1.8.0)
SELECT * FROM cypher('fraud', $$
  MERGE (p:Person {ext_id: $ext_id})
  ON CREATE SET p.created_at = '2026-10-19'
  ON MATCH  SET p.updated_at = '2026-10-19'
$$) AS (p agtype);

The sharp edges, all documented behavior, all manageable:

  • Every cypher() call must declare its output columns: AS (m agtype). The planner treats it as a function returning SETOF record. It cannot appear inside expressions — use a subquery in FROM.
  • Parameters require prepared statements (the map argument errors otherwise).
  • It is an openCypher subset converging toward, not conforming to, the language: no graph type system/schema clause, no GQL composition operators, some list/collection semantics differ, and the community files real gaps (e.g., label-pattern-expression fixes landed in 1.8). Ported Neo4j queries need testing, not trust.
  • Return values are agtype: map/list/scalar superset of JSONB. You often want (v->'name')::text-style extraction (or 1.8's composite vertex/edge types with direct field access) rather than shipping agtype to the app.

7 · Variable-length paths: the honest cost model

VLE ([*1..k]) is where graph queries pay for combinatorics. The 2026 discussion around AGE issue #2349 is worth reading because it is precise: AGE's VLE enforces edge uniqueness (openCypher edge-isomorphism — vertices may repeat via different edges), the output size on cyclic graphs grows combinatorially, and the fix is semantic care (bounded hops, relationship-type filters — 1.8 added relationship-type filters and a minimum hop count), not a "visited set" that would silently change semantics. The 1.8.0 line shipped the real engineering answer: hash-adjacency + flat-array edge structures, terminal-qual rewrite, VLE caching, and a documented cost-model note.

VLE checklist before production
  • Hop bounds always present ([*1..k], never [*])
  • Edge labels constrained on every hop where the domain knows them
  • Endpoint indexes exist (start_id/end_id, id columns since 1.7)
  • Measure on a cycle-rich slice of real data, not a tree-shaped toy dataset
  • Compare against a hand-written recursive CTE (UNION dedup) — sometimes the SQL is faster and exact to your intent (see #2349's measurements: CTE 0.34 ms vs VLE 23 ms at one benchmark shape)

8 · SQL/PGQ: the standard — and the PostgreSQL 19 story as of October 2026

SQL:2023 added SQL/PGQ (ISO/IEC 9075-16): CREATE PROPERTY GRAPH defines a read-only graph view over existing tables (vertices/edges = tables, keys required), and GRAPH_TABLE(g MATCH (c IS customer)-[IS has_placed]->(o IS "order") COLUMNS (...)) embeds graph patterns in ordinary SQL. Oracle ships it; DuckDB ships it via DuckPGQ; Neo4j's engineers influenced the design. The PostgreSQL community tried to ship it in PostgreSQL 19 — and the honest current status, as of this report's October 2026 window:

As of 2026-10-19

SQL/PGQ was committed and visible in the PostgreSQL 19 beta docs (CREATE PROPERTY GRAPH, GRAPH_TABLE, "conforms to ISO/IEC 9075-16") but the release team reverted it on 2026-09-07 over unresolved catalog/dump-restore design questions (orphaned graph metadata, label scoping, pg_class membership, dependency loops). PostgreSQL 19 GA (planned 2026-11-19) ships without it; a comeback is aimed at v20. Do not write migrations against beta syntax. Until then the ladder is: recursive CTEs, AGE, or — on other engines — standard SQL/PGQ support (Oracle 23ai/26c, DuckDB+DuckPGQ for analytics).

The strategic read matches Percona's: the syntax is standard, the collaboration is multi-vendor, and the missing piece is engine-level indexing for graph patterns. If it lands in v20 and index support follows, many "shallow graph" workloads stop needing any extension at all. Watch, don't bet the roadmap.

10 · A worked production schema (SQL + Cypher side by side)

Fraud-screening graph in Postgres: typed facts stay relational (auditable, indexed, constrained), the relationship pattern lives in AGE, and the query composes both in one transaction:

CREATE EXTENSION IF NOT EXISTS age;

CREATE TABLE accounts (
    account_id   bigint PRIMARY KEY,
    customer_id  bigint NOT NULL,
    country      text   NOT NULL,
    opened_at    timestamptz NOT NULL,
    status       text   NOT NULL DEFAULT 'active'
);
CREATE INDEX ON accounts (customer_id);

SELECT create_graph('fraud');
-- labels (:Account, :TRANSFERS_TO, :USES_DEVICE, ...) materialize lazily as
-- tables when first used; the ingestion trigger below is what populates them.

Ingest keeps SQL as source of truth and the graph as a derived projection in the same commit:

CREATE FUNCTION project_transfer() RETURNS trigger AS $$
BEGIN
  PERFORM set_config('search_path', 'ag_catalog, "$user", public', true);
  SELECT * FROM cypher('fraud', $$
    MERGE (a:Account {id: $from})
    MERGE (b:Account {id: $to})
    MERGE (a)-[e:TRANSFERS_TO {tx_id: $tx}]->(b)   -- tx_id keeps edges idempotent
    ON CREATE SET e.amount = $amt, e.at = $at
  $$, '{"from":1001,"to":2002,"tx":88001,"amt":2500,
       "at":"2026-10-19"}') AS (v agtype);
  RETURN NEW;
END $$ LANGUAGE plpgsql;

Screening query: relational predicates do the contract, Cypher finds the ring shape:

SELECT c.*
FROM   cypher('fraud', $$
         MATCH (a:Account {id: $acct})-[:TRANSFERS_TO*1..3]->(x:Account)
         RETURN DISTINCT x.id
       $$, '{"acct":1001}') AS (suspect agtype)
JOIN   accounts a   ON a.account_id = (suspect::jsonb ->> 'id')::bigint
JOIN   customers c ON c.customer_id = a.customer_id
WHERE  a.status = 'active' AND a.country IN ('US','DE')   -- typed filters, explainable
ORDER  BY a.risk_score DESC;                              -- plans you can read

That is the whole system: one database, one transaction manager, graph patterns where patterns pay, SQL everywhere else. The costs — trigger-path complexity, openCypher subset testing, hop-depth tuning — are real but ordinary database work.
