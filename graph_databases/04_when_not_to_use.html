When a graph database
is the wrong tool.

"Everything is a graph" is how careers get made and budgets get burned. Most connected data is already a working graph inside the relational database you operate. This page draws the line: ten hard "don't" rules, the anti-pattern catalog, the privacy ledger, the vendor-consolidation warning this category earned in 2025, and — to stay honest — the short list of triggers where a dedicated graph database is genuinely the right call.

1 · Ten rules: do not use a dedicated graph database when…

  1. …your traversals are 1–2 hops over indexed keys. A JOIN with a B-tree is already an O(log n) edge lookup, exact, and explainable. The index-free-adjacency advantage is a depth-and-fanout effect; at two hops it's noise. If the SQL is obvious, the SQL is correct.
  2. …you haven't measured your hop profile. Write down the actual queries: max depth, branching factor, start sets. Teams that buy graph engines for "connected data" and then discover their top 50 queries are all ≤2 hops have bought a second DBA. (The one PostgreSQL 19 feature the release team itself recommends instead: recursive CTEs.)
  3. …the relationships are typed facts under constraint. "This order belongs to this customer" wants a foreign key, a CHECK, and RLS — not a label and hope. Property graphs' flexibility is a modeling liability when the schema is the contract.
  4. …the workload is actually whole-graph analytics. PageRank/communities over everything is OLAP: batch it in NetworkX/Graph-tool/pgRouting/GDS/TigerGraph-class tooling. Running analytics scans on your transactional graph store (or vice versa) is this category's most common architecture error.
  5. …the graph would be a second source of truth you must sync. Every dual-store comes with sync lag, reconciliation jobs, and a stale-answer incident class (see §6). If Postgres holds the facts, keep the graph derived — or keep it inside Postgres (AGE) where sync is a trigger, not a pipeline.
  6. …your team doesn't speak the query language and the hiring pool is thin. Cypher is learnable; GQL/Gremlin/GSQL estates are not interchangeable; graph modeling (supernodes, path semantics, property vs relationship decisions) is a skill with a learning curve that shows up as silent query bugs. A database nobody on-call can query is an outage generator.
  7. …exact licenses or operational posture rule it out. Neo4j Community is GPLv3 with clustering/enterprise features gated; some embedded options are effectively unowned (see §4); managed graph services are unit-priced and often the priciest way to hold data you could keep next to the source. Decide against your actual license/compliance/Ops constraints, not a demo.
  8. …your data contains supernodes you haven't modeled. One node with millions of edges flattens every engine's latency story. If the domain has unavoidable hubs (platform accounts, default tenants), you must shard/dodge them anyway — no vendor benchmark with a nice power-law dataset will save you.
  9. …deletion obligations can't be honored in the store. GDPR erasure in a graph is surgery: delete a node and its edges, recompute anything derived (components, embeddings, community summaries), in replicas and backups. If a candidate store makes that unverifiable, it fails on Day 0 — §3 explains why graph deletion is harder, not easier, than row deletion.
  10. …you don't yet have the problem. "Our data is connected" is not a requirement; a named query that JOIN-spaghetti failed is. Every legitimate graph project starts from a query you can write down and time.

3 · The privacy ledger: edges are personal data too

Three graph-specific privacy facts every architecture decision should inherit:

  • Relationships are the sensitive part. A friendship graph, a transaction graph, or an org graph carries information that no single node does: who knows whom, who really owns which company, who moves money through whom. The canonical demonstrations: the Netflix Prize dataset was re-identified from public IMDB ratings (2007), and the 2018 Strava activity heatmap exposed military installations through the edges between places. "We only published/anonymized nodes" is not a control when the topology itself is the payload.
  • Re-identification through linkage is stronger on graphs. Two "anonymized" graphs of the same people (or one graph + any auxiliary attribute data) can be matched by structural signatures; the research literature on de-anonymizing social graphs (Narayanan-Shmatkov-style linkage attacks, Twitter-graph exposure incidents) is old and settled: graph structure alone identifies.
  • Erasure is graph surgery. GDPR/retention deletion must remove the node, all its edges, and propagate through derived artifacts — closure tables, component ids, community summaries, GraphRAG extractions, analytics snapshots. In Postgres+AGE this is one transaction with a trigger cascade (plus replicas/backups like any table); in multi-store setups it's a workflow you must be able to prove. Design the DELETE path before the first INSERT.
Compliance rule

A graph over personal data inherits the classification of its most sensitive edge — and adds a duty ordinary tables don't have: prove the structure is safe to expose (or is access-controlled) and that deletion leaves no dangling relationships. "The graph DB isn't PII because names are on only some nodes" is not a lawful position.

4 · The consolidation ledger: what Kuzu taught everyone

In October 2025 the only mainstream embedded graph database vanished in a week: Kuzu (MIT-licensed, University-of-Waterloo lineage, the SQLite-of-graphs) was archived (2025-10-10) after Apple acquired Kùzu Inc. (deal 2025-10-09); the last release, 0.11.3, is frozen — no security fixes — and the ecosystem scattered into forks (LadybugDB, Bighorn, RyuGraph, Vela, pg_ladybug, NeuG). The graph category has precedent beyond it: Memgraph changed hands twice in two years; the 2020–2022 graph-DB funding cohort consolidated hard. Evaluation consequences:

  • Check the sponsor, not just the license. MIT without a maintainer is a ticking dependency (see projects pinning kuzu==0.11.3 in 2026 and calling it a risk). Ask: who pays the committers, what's the release cadence this year, is there a paying company or a foundation PMC (AGE, as Apache, scores well here)?
  • File formats and storage versions churn across forks. Kuzu's single-file format changed late; forks don't open each other's files. Storage longevity is an operational property of a graph database — verify it like you'd verify backup restore.
  • Postgres is the counter-position. The engine at the center of this repo has a 30-year release record and an extension ecosystem under a foundation — the graph capability ladder (Part 2) is the low-regret path while the startup layer consolidates.

5 · When a dedicated graph database IS the right answer

Honesty requires the inverse list. Each trigger is checkable — if you can't point to one in writing, stay on the ladder:

  • Deep traversal at high concurrency is the product's critical path. If every request walks 3–6+ hops with wide fan-out (fraud screening, network impact, GraphRAG retrieval), native index-free adjacency is a measured win. Put your hop profile in the design doc before the POC.
  • Whole-graph analytics as a live feature at scale: Neo4j GDS, TigerGraph, or Neptune Analytics (in-memory, "tens of billions of relationships" per AWS, algorithms + vector) exist for exactly this. Postgres extensions don't cover GDS-class algorithm catalogs at that throughput.
  • Petabyte-scale / mandatory distribution: TigerGraph-class MPP keeps latency stable at 10+ hops across billions of edges (their benchmark framing — verify on your data); single-node engines, AGE included, don't.
  • Hard isolation between graph workload and the OLTP system — a query spike must never touch the transactional database; the separate store is a firewall, not redundancy.
  • First-class graph tooling is the differentiator: Neo4j's ecosystem (Bloom, GraphDataScience, neo4j-graphrag, Cypher tooling) compresses a year of app-tier work; Memgraph's streaming (Kafka/Pulsar) fits real-time ops graphs; ArcadeDB's multi-model + Apache-2.0 fits embedding constraints Postgres already can't meet.

6 · Primary DB + graph index: the dual-store compromise

When §5 triggers are real but Postgres remains the source of truth, the 2026 pattern matches the vector report's: primary database holds facts and lifecycle; the graph holds a derived projection; sync is explicit (outbox / logical decoding / connector), never best-effort dual writes. Graph-specific additions to the runbook: edge deletions must be propagated (a forgotten edge is a false connection — worse than a missing one in fraud work), analytics artifacts (component ids, communities) lag by the batch interval and must carry freshness, and the erasure workflow (§3) must cross both stores with proof. Test the boundary with a concrete question: what does the fraud screen return during a 10-minute sync outage? If the honest answer matters, the in-database ladder (Part 2, AGE included) was the right architecture.

7 · The decision tree, in words

  1. Do you have a named query with hop depth ≥3 or real fan-out, or a relationship-shaped domain fact (typed, dated, scored)? No → SQL/JOIN/recursive CTE. Done. Most products stop here — this is the majority answer, not a consolation prize.
  2. Is the data in Postgres (or fine living there)? Yes → climb the ladder: recursive CTE → ltree → pgRouting → AGE, measuring at each rung. (SQL/PGQ over tables is the future standard; not GA in Postgres as of Oct 2026 — don't code against betas.)
  3. Workload split? OLTP traversal deep & hot → native OLTP engine (Neo4j/Memgraph/Neptune). OLAP whole-graph → analytics stack (GDS/TigerGraph/Neptune Analytics/in-process libs). Both → separate them deliberately, don't make one machine serve both.
  4. Scale wall crossed? Billions of edges / mandatory distribution / supernode storms → distributed MPP or managed, accepting the ops weight and the license terms.
  5. Hard constraints override: determinism & audit → relational/AGE with explainable plans, never an opaque pipeline; privacy → graph structure is personal data, deletion path proven first; vendor risk → prefer foundation governance (Postgres, Apache AGE) while the startup layer consolidates.
  6. Whatever you pick: write down the acceptance numbers ("6-hop screening query ≤ 250 ms p95 at 200 QPS on our 40 M-edge graph") and re-measure at every upgrade. The number, not the brand, is the architecture — even if every vendor's page disagrees.

8 · Sign-off checklists

Before adding any graph technology
  • Named queries written down with hop depth and expected fan-out
  • Current Postgres baseline measured (plan + latency) — the number to beat
  • Workload classified OLTP-traversal vs OLAP-analytics (or split planned)
  • Supernodes and cycles identified in a real data slice
  • Deletion/erasure path designed end-to-end, including derived artifacts
Before production (Postgres ladder)
  • Traversal predicates indexed; recursive CTE cycle-guarded (UNION or path array + depth cap)
  • AGE: extension + PG version pair verified (1.8.x ↔ PG11–18), upgrade rehearsal done with backup
  • Property indexes (GIN containment opclass) + endpoint indexes (start_id/end_id) exist
  • VLE bounds enforced in application review; relationship-type filters on hot paths
  • RLS/grants planned over label tables; cypher() output typed to text/numeric at the boundary
  • EXPLAIN reviewed for seq scans and nested-loop blowups on the top 10 graph queries
  • Recall-free but correctness-harnessed: golden fixtures for pattern semantics (VLE edge-uniqueness, null handling)
  • Backup/restore + pg_upgrade rehearsal includes graph schemas
