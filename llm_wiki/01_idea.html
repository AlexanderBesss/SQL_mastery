Part 1 of 5 · The idea

Stop retrieving.
Start compiling.

The interesting thing about Karpathy's LLM Wiki is not that it stores notes in markdown. It is that it moves the expensive part of knowledge work — synthesis, cross-referencing, noticing contradictions — from query time to ingest time. The wiki is a compiled artifact that gets better as you use it.

1 · The RAG baseline: capable, but amnesiac

Retrieval-augmented generation is the default way to give a model access to documents. You chunk the documents, embed the chunks, put the vectors in an index, retrieve the top k chunks for a question, and ask the model to answer from them. It is a good architecture for point-source lookup. Ask "what is the refund window in the 2024 policy?" and RAG is exactly the right shape: find the clause, quote it, done.

The limitation appears when the question requires synthesis across several documents. The retriever may miss one of the relevant chunks. Even when it finds them all, the model has to rediscover the same relationships, reconcile the same contradictions, and rebuild the same comparison on every query. Then the context window closes and the synthesis is gone. The next question starts from zero.

Every queryChunk + embedDocuments are split and indexed ahead of time.
Every queryRetrieve top-kSimilarity search returns fragments, not a model of the domain.
Every querySynthesizeThe model reconciles the fragments and writes an answer.
Every queryAnswerCitations point at chunks; the synthesis exists only in the response.
Every queryDiscardNothing accumulates. The next question repeats the work.

Karpathy's framing is blunt: with RAG, "the LLM is rediscovering knowledge from scratch on every question. There's no accumulation." That is not a bug in a retrieval pipeline; it is what a stateless pipeline does. RAG optimizes for finding evidence, not for maintaining a point of view.

The RAG counter-argument

RAG is not obsolete. It is cheaper to build, easier to update when documents change, and better when the corpus is huge, unstructured, or queried once. The LLM Wiki is a different product: a durable synthesis layer for a corpus you will revisit. Part 5 shows that agentic RAG can match the wiki on some question sets at lower token cost — which is exactly why the choice should follow the workload, not the hype cycle.

2 · The alternative: a persistent, compiled wiki

The LLM Wiki inserts a layer between you and the raw sources. The raw collection stays immutable. The wiki is a directory of markdown pages that the agent owns and maintains. The schema is a document that tells the agent how the wiki is structured and how to behave. When a new source arrives, the agent compiles it into the existing wiki rather than merely indexing it.

New sourceIngestThe agent reads the raw source and discusses the key takeaways with you.
CompileUpdate pagesSource summary, entity pages, concept pages, comparisons, index, log.
AskQuery the wikiThe agent reads the index, follows links, and answers with citations.
File backKeep the answerA good comparison or synthesis becomes a new wiki page.
PeriodicallyLintFind contradictions, stale claims, orphans, broken links, and gaps.

This is the core inversion: the expensive synthesis happens once, at ingest, and is maintained rather than re-derived on every query. The cross-references are already in the pages. The contradictions have already been flagged. The comparison already exists. A query can start from a page that represents the current state of your understanding, not from a pile of chunks that may or may not contain it.

"The wiki is a persistent, compounding artifact. The cross-references are already there. The contradictions have already been flagged. The synthesis already reflects everything you've read."

Andrej Karpathy, LLM Wiki, 4 April 2026

The three layers

Raw sources

Articles, papers, images, transcripts, datasets. Curated by you, read by the agent, never modified by it. This is the source of truth and the audit trail.

The wiki

Summaries, entity pages, concept pages, comparisons, an overview, syntheses. The agent owns this layer entirely: it creates, updates, links, and reconciles.

The schema

Usually AGENTS.md or CLAUDE.md. It defines the directory layout, page types, frontmatter, naming, link conventions, ingest/query/lint workflows, citation rules, and the boundaries the agent must not cross. This is the file that turns a generic chatbot into a disciplined maintainer.

Karpathy calls the schema "the key configuration file" and says you and the LLM co-evolve it. That is an important detail: the schema is not a static prompt. It accumulates rules as you learn what goes wrong. A good schema is scar tissue from real mistakes — a missing citation, a stale index, an agent that edited a raw source, a summary that inflated a number.

What gets compiled

A single source might touch ten to fifteen pages. For a research paper, the agent might create or update:

  • a source summary page with the citation, date, and key claims;
  • an entity page for each person, organization, or system the paper is about;
  • a concept page for each method or idea it advances;
  • a comparison page if the paper contradicts or extends an existing approach;
  • the overview or thesis page if the new evidence changes the big picture;
  • the index and the log.

This is more work than writing a summary. It is also the work that makes the wiki useful six months later. The summary is a leaf; the cross-references are the structure that lets you navigate from a question to the evidence without re-reading the corpus.

3 · What "compounding" actually means

Compounding is not "the model remembers the chat." The chat is still ephemeral. What persists is the artifact: pages, links, citations, and the current synthesis. Each new source can strengthen, weaken, or complicate that synthesis. Each good answer can become a new page, so the act of asking a question also improves the knowledge base.

Positive loop
  1. You add a paper.
  2. The agent updates the concept page and flags a contradiction.
  3. You ask a comparison question.
  4. The answer resolves the contradiction and is filed back.
  5. The next question starts from the resolved comparison.
Negative loop
  1. The agent writes a plausible but wrong summary.
  2. Four pages cite the summary.
  3. A later page cites those four pages as evidence.
  4. The wiki is internally consistent and externally wrong.
  5. Lint, which reads the wiki, sees no contradiction.

Both loops are real. The pattern's advocates talk about the first; its critics talk about the second. The difference is not the LLM's intelligence. It is whether the system has provenance (links back to the raw source), review gates (a human promotes drafts to trusted), and deterministic checks (the source exists, the link resolves, the number matches). Those are engineering decisions, not prompt wording. Part 5 covers them in detail.

Compounding is a property, not a guarantee

A wiki can compound knowledge or compound errors. It depends on whether every claim can be traced to a source, whether a human ever reads the output, and whether the lint pass compares claims against the raw bytes rather than only against other wiki pages. "The wiki is internally consistent" is not the same as "the wiki is true."

4 · Why maintenance is the real bottleneck

The standard failure mode of a personal wiki is not capture. It is maintenance. Updating cross-references, keeping summaries current, noticing that a new source contradicts an old claim, and maintaining consistency across dozens of pages is tedious, unbounded work. Humans start with enthusiasm and abandon the wiki when the maintenance burden grows faster than the value.

Karpathy's argument is that this is precisely the work an LLM is good at. It does not get bored, it does not forget to update a cross-reference, and it can touch fifteen files in one pass. The cost of maintenance approaches zero in human attention, even though it is not zero in tokens. The wiki stays alive because the thing that killed it — bookkeeping — is automated.

JobHumanAgent

The division of labour is the actual innovation. It is not "the AI writes my notes for me." It is "the AI does the maintenance that made me abandon my notes, while I keep doing the thinking that makes them worth maintaining."

5 · What is new — and what is not

Karpathy's idea file is careful about lineage: it explicitly compares the pattern in spirit to Vannevar Bush's Memex (1945), a personal, curated knowledge store with associative trails between documents. The connections between documents were supposed to be as valuable as the documents themselves. Bush could not solve who would maintain the trails. The LLM handles that part.

  • 1945 · MemexVannevar Bush imagines a private, curated knowledge store with associative trails. The maintenance problem remains open.
  • 1950s–1990s · Zettelkasten and hypertextAtomic notes, explicit links, and associative navigation. Niklas Luhmann's slip-box is the canonical manual version.
  • 2001–2020 · Wikis and graph viewsWikipedia, personal wikis, Roam, Obsidian, Logseq. Markdown links and backlinks become a mainstream way to think in a graph.
  • 2020s · RAG and agentic retrievalVector search, hybrid retrieval, and tool-using agents make large document collections queryable. Synthesis remains mostly per-query.
  • April 2026 · LLM WikiKarpathy combines the pieces: an LLM maintains a persistent interlinked markdown wiki between the raw sources and the questions. Compile once, query many.
  • June–July 2026 · Open Knowledge FormatGoogle Cloud formalizes the shape as a portable markdown + YAML-frontmatter bundle, then adds provenance, trust, lifecycle, and attestation in v0.2.

So what is genuinely new? Three things:

  1. The maintainer is an agent. Prior systems assumed a human would keep the links and summaries current. The agent makes maintenance cheap enough to sustain.
  2. The synthesis is an artifact, not a response. Answers can be filed back into the wiki, so exploration compounds instead of disappearing into chat history.
  3. The schema is executable culture. A plain-language AGENTS.md can encode page types, citation rules, review gates, and workflows. The agent can follow it across sessions without a bespoke application.
Attribution, precisely

Karpathy's contribution is the pattern — the three layers, the three loops, and the human/agent division of labour — not the invention of markdown, wikilinks, graph views, or knowledge graphs. If someone tells you he invented "storing markdown as a graph," the accurate version is: he popularized an LLM-maintained wiki whose links form a graph, and he wrote the idea down in a form other agents could implement.

6 · Where the pattern fits

Karpathy lists personal goals and health, research, reading a book, business/team knowledge, competitive analysis, due diligence, trip planning, course notes, and hobby deep-dives. The common thread is accumulating knowledge over time where you want the connections, not just the documents.

Use caseWhat compoundsMain risk
Research deep-diveA thesis, an evidence map, comparisons across papers, a list of open questions.Confidently wrong synthesis; source drift; citation inflation.
Reading a bookCharacter, theme, place, and plot-thread pages; a companion wiki by the final chapter.Over-summarizing; losing the author's nuance; spoilers everywhere.
Personal goals / journalPatterns across entries, recurring obstacles, decisions and their outcomes.Sensitive data in a plaintext repo; over-trusting the agent's interpretations.
Team/internal wikiProject context, decisions, meeting outcomes, customer calls, onboarding knowledge.Permissions, oversharing, stale process docs, no clear owner.
Competitive / due diligenceEntity pages, claim comparisons, timelines, contradiction flags.Source quality; unconscious bias; unreviewed claims becoming "facts."
Course notes / hobbyConcept pages, worked examples, links to prerequisites, a growing map of the field.Volume bloat; writing without revisiting; low-value pages.

The pattern is weakest when the corpus is a one-off. If you will never ask a second question, a RAG pipeline or even a long-context prompt is simpler. It is strongest when the same domain gets new sources every week and the questions get more ambitious over time.

7 · What it feels like in practice

Karpathy's described setup is deliberately low-tech: an LLM agent on one side, Obsidian on the other. The agent edits markdown files based on the conversation; the human browses the results in real time, follows links, checks the graph view, and reads the updated pages. The tool is not a chat window with a document attached. It is a working directory that both parties can inspect.

Three mental shifts follow:

  • From chat history to files. The durable state is on disk, diffable in git, readable without the model. You can open a page six months later and know where it came from.
  • From retrieval to navigation. The agent does not just search; it reads the index, follows links, and assembles context from pages that already contain the synthesis.
  • From answers to artifacts. A good answer should not disappear into the conversation. If it is useful, it becomes a page. The wiki is the memory; the chat is the workbench.
The uncomfortable part

This only works if you actually read and revisit the wiki. A write-only wiki is an expensive content-generation habit. The feedback loop that keeps it honest is the human opening pages, asking questions, checking citations, and correcting the agent. If you will not do that, do not build it.

8 · Comparison: RAG, wiki, long context, graph

ArchitectureWhat persistsWhen synthesis happensStrengthWeakness
Single-round RAGThe index and raw chunksEvery queryCheap, simple, good for point lookupsNo accumulation; weak on multi-source synthesis; retrieval misses compound
Agentic RAGThe index and raw chunksEvery query, with multiple retrieval/read stepsCloses much of the synthesis gap at lower cost than a wiki in some testsMore turns and latency; still no durable synthesis artifact
LLM WikiThe compiled pages, links, index, and logAt ingest, then maintained by lintCompounding synthesis; human-readable; git-native; strong claim-level citationsIngest cost; error compounding; staleness; maintenance discipline
Long contextNothing (or a cached prompt)Every queryNo retrieval pipeline; good for a single large documentExpensive per query; context limits; no cross-session accumulation
GraphRAG / graph DBEntities and typed relationshipsAt extraction, then queriedMulti-hop and global questions; explicit structureExtraction cost and errors; ontology maintenance; overkill for small corpora
Plain notes / wikiHuman-written pagesWhen a human writes themCheap, familiar, high trustMaintenance burden; links rot; summaries go stale

The LLM Wiki is closest to "plain notes" in storage and closest to "GraphRAG" in ambition. The difference is that it uses prose and links as the graph, and it uses an agent to keep the graph alive. It is not trying to replace a database. It is trying to make a personal knowledge artifact sustainable.

9 · Working glossary

TermMeaning in this report
Raw sourceAn immutable input document: article, paper, image, transcript, dataset. The agent reads it but never edits it.
Wiki pageAn LLM-generated markdown page: summary, entity, concept, comparison, synthesis, or overview.
SchemaThe AGENTS.md / CLAUDE.md contract that tells the agent how the wiki is structured and how to behave.
IngestThe workflow that compiles a new raw source into the wiki: read, discuss, write, link, index, log.
QueryAnswering a question from the wiki with citations, and optionally filing the answer back as a page.
LintA health check: contradictions, stale claims, orphans, broken links, missing pages, missing cross-references, data gaps.
WikilinkA link such as [[concept-rag]] that points to another page. Obsidian, Logseq, and many wiki tools understand it.
BacklinkThe reverse edge: which pages link to this page. Backlinks are how you discover context you forgot to look for.
Graph viewA visualization of pages and links. Useful for shape and orphans; not a query engine by itself.
OKFOpen Knowledge Format: Google Cloud's markdown + YAML-frontmatter bundle spec that formalizes the LLM-wiki shape.
ProvenanceThe link from a wiki claim back to the raw source and the date it was checked. Without it, the wiki is unfalsifiable.
Five takeaways from Part 1
  1. The innovation is timing. Compile synthesis at ingest instead of re-deriving it at query time.
  2. The artifact is the memory. Chat history is not a knowledge base; files with links and citations are.
  3. Maintenance is the bottleneck. The agent's real job is the bookkeeping humans abandon.
  4. Compounding cuts both ways. A persistent wiki can accumulate truth or confidently repeat errors.
  5. It is a synthesis tool, not a database. Use it where you will revisit a domain and care about connections.
