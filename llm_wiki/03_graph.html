Part 3 of 5 · Markdown as a graph

A folder is a graph
if you read the links.

Every markdown file is a node. Every link is a directed edge. Folders add containment, headings add sections, frontmatter can add typed relationships, and backlinks turn the graph around. The interesting question is not "graph or no graph" — it is which graph layer earns its keep.

1 · Markdown is already a graph

The graph does not need a special file format. A markdown wiki already has nodes and edges:

  • Files are nodes. wiki/concepts/rag.md is a node with a title, a body, and metadata.
  • Links are directed edges. [[concept-llm-wiki]] in the RAG page is an edge from RAG to LLM Wiki.
  • Folders are containment edges. wiki/concepts/ contains the concept pages; the tree is a hierarchy.
  • Headings are section nodes. A long page can be a tree of sections, which is useful for section-level retrieval.
  • Frontmatter can add typed edges. A relationship such as contrasts_with or founded can carry a predicate, source, evidence, and confidence.
  • Tags are membership edges. A tag is a many-to-many grouping that cuts across the folder tree.

This is why "store markdown like a graph" is both true and misleading. The files are not stored in a graph; they are stored in a directory. The graph is a view over the directory: parse the links, resolve the paths, and you have nodes and edges. That view can be built in memory, in a search index, or in a graph database. The files stay the source of truth.

2 · Link syntax and direction

There are two link families in a typical markdown wiki. Wiki-style links are compact and first-class in Obsidian, Logseq, and many personal wiki tools. Standard markdown links are portable and are what OKF uses.

SyntaxMeaningNotes
[[concept-rag]]Link to a page by slugObsidian-style. Resolution depends on the tool's link settings.
[[concept-rag|RAG]]Link with display textThe alias is presentation; the edge points at the target.
[[concept-rag#trade-offs]]Link to a headingUseful for section-level navigation and citations.
![[diagram.png]]Embed an imageAn embed is a containment/transclusion edge, not just a link.
[RAG](/concepts/rag.md)Standard markdown linkPortable; OKF's recommended bundle-relative form starts with /.
[trade-offs](/concepts/rag.md#trade-offs)Standard link to a headingWorks on GitHub, in static site generators, and in most editors.
[[not-yet-written]]Unresolved linkNot necessarily an error. It can be a placeholder for future knowledge.

Direction matters. If page A links to page B, the graph has an edge A → B. The backlink is the reverse view: "B is referenced by A." Most wiki tools show backlinks automatically. A graph database can answer the same question with one indexed lookup instead of scanning every file.

A link is not a relationship type

A plain link says "this page references that page." It does not say whether the relationship is supports, contradicts, supersedes, is an example of, or merely mentions. That distinction is the difference between a link graph and a knowledge graph. You can add typed edges in frontmatter, but most wikis do not need them on day one.

3 · Backlinks and graph views

Obsidian's graph view is the reference viewer in Karpathy's setup. It renders pages as nodes and links as edges, with a local graph for the current page and a global graph for the vault. The backlinks pane shows inbound links. The graph view is genuinely useful for seeing shape: which pages are hubs, which are orphans, which clusters are connected, and where the wiki is a hairball.

But a graph view is a visualization, not a query engine. It does not answer "shortest path from this source to that concept," "which pages have no citations," or "what changed downstream of this claim." Those require a graph index or a script. Treat the view as a map, not a database.

What the graph view is good for
  • Spotting orphans and disconnected clusters.
  • Seeing which pages act as hubs.
  • Checking whether the wiki has a navigable shape.
  • Exploring a neighborhood you did not know existed.
What it cannot do
  • Traverse to a depth and return a path.
  • Rank by centrality or community.
  • Check that every claim has a source.
  • Tell you whether the link is semantically correct.

Topology: aim for a tree, not a hairball

A common failure is a star-shaped wiki where one overview page links to everything and every new page attaches to the same gravity well. The result looks connected but is hard to navigate: every path goes through the hub, and the graph view becomes a hairball. A better shape is a tree of clusters: an index at the top, a hub per cluster, member pages that link up to the hub and sideways to siblings, and sources/syntheses as leaves.

index.md
└── overview.md
    ├── cluster: retrieval
    │   ├── hub: retrieval.md
    │   ├── concept: rag.md
    │   ├── concept: vector-search.md
    │   └── comparison: rag-vs-wiki.md
    ├── cluster: knowledge-maintenance
    │   ├── hub: llm-wiki.md
    │   ├── concept: ingestion.md
    │   └── concept: lint.md
    └── sources/
        ├── source-karpathy-llm-wiki.md
        └── source-rag-vs-wiki-study.md

This is a design heuristic, not a law. The point is to make navigation predictable: from any page, you can go up to its cluster hub, sideways to a sibling, or down to evidence. Karpathy's index file plays the role of the top-level map; the cluster hubs keep the graph from collapsing into a single star.

4 · Typed edges and provenance

Plain links are enough for navigation. If you want the graph to support claims like "this method supersedes that one" or "this person founded that company," you need typed edges. The usual way to add them to markdown is YAML frontmatter.

---
type: concept
title: LLM Wiki
graph:
  node_id: concept:llm-wiki
  node_type: concept
  relationships:
    - predicate: contrasts_with
      object: concept:rag
      source: source-karpathy-llm-wiki
      evidence: "RAG rediscovers knowledge on every query; the wiki compiles it once."
      confidence: high
      status: current
    - predicate: depends_on
      object: concept:markdown-graph
      source: source-karpathy-llm-wiki
      evidence: "A structured, interlinked collection of markdown files."
      confidence: high
      status: current
---

A typed edge should carry more than a predicate. The useful fields are:

  • predicate — what kind of relationship it is;
  • object — the target node;
  • source — the page or raw file that supports the claim;
  • evidence — a quote or precise pointer, not a vibe;
  • confidence — high / medium / low;
  • status — current / historical / proposed / disputed / superseded.

This is the model used by community graph layers such as llm-wiki-plugin. The important discipline is that the extractor must not invent edges: if there is no source and no evidence, the edge is a mentions link at best. An ontology file can declare which predicates are allowed and which node types they connect, so lint can validate the graph instead of trusting the model's prose.

Typed edges are optional; provenance is not

You can run a perfectly useful LLM Wiki with plain [[wikilinks]] and no ontology. What you cannot skip is the link from a claim back to its source. A typed edge without evidence is more dangerous than an untyped link, because it looks more authoritative. Add types when they answer real questions; add provenance from day one.

5 · Graph indexes: ki, Neo4j, and the filesystem

A graph index parses the markdown, builds nodes and edges, and stores them where traversal and reverse lookup are cheap. It does not replace the files. The best reference implementation for this pattern is ki (knowledge-index), which syncs a folder of markdown to Neo4j and exposes navigation commands to an agent.

The ki model

Node / edgeMeaning
VaultThe corpus root.
FolderA directory in the vault.
DocumentOne .md file. Linked non-markdown files become stub nodes.
SectionA heading-bounded subsection. Each document is a tree of sections.
:HASContainment: Vault → Folder → Document → Section.
:NEXT_SECTIONReading order between sections.
:LINKS_TOEvery wikilink / markdown link, including external URLs.

The model is deliberately small. It does not try to infer an enterprise ontology. It gives the agent a map: where a document sits, what sections it contains, what follows what, and what links to what. Because construction is deterministic and idempotent, the index is a disposable cache: delete it and rebuild from the files.

# Build / sync the index (conceptual; see the ki repo for exact commands)
ki index ./my-wiki

# Navigate
ki search "rag vs wiki"
ki tree concept-llm-wiki
ki neighbors concept-rag
ki path source-karpathy-llm-wiki concept-qmd
ki backlinks concept-llm-wiki

Neo4j's argument for this layer is that a filesystem scales linearly: grep reads every file, resolving each link is another pass, and "what points at this page?" has no index. A graph index turns a hop into a pointer and makes backlinks a native query. That is technically fair, but it is a vendor argument. At a few hundred pages, the filesystem is usually fast enough. The index earns its keep when traversal and backlinks are frequent, or when many agents share the same vault.

What a graph database adds

OperationFilesystem + grepGraph index
Find a page by keywordFast with an index file or search toolFast with a full-text index
Follow a linkOpen the file, parse the link, open the targetPointer / indexed edge
BacklinksScan every file or maintain a cacheNative reverse edge
k-hop traversalk passes over the corpus (or a precomputed cache)Cost tracks the neighborhood, not the corpus
Shortest pathCustom BFS over parsed linksNative path query
Centrality / communitiesExport and run an analytics libraryGraph Data Science or in-process library
Section-level retrievalParse headings and chunks yourselfSection nodes with reading order

Notice that search and navigation are different columns. A vector index can find semantically similar pages but cannot tell you what links to them. A graph index can traverse links but is not a good semantic search engine by itself. Mature systems often combine both: lexical + vector search for discovery, graph traversal for context, and a reranker for the final order.

6 · When a graph index earns its keep

SituationRight layerWhy
Personal wiki, under ~100 pagesIndex file + grep + Obsidian graph viewNo infrastructure. The index is enough and the graph view is a useful map.
100–1,000 pages, mostly keyword questionsLocal hybrid search (qmd)Section-level retrieval and reranking; still no graph server.
Frequent "what links here?" and multi-hop questionsGraph index (ki / Neo4j)Backlinks and traversal are native; the index is rebuildable.
Typed domain model with entities and predicatesGraph index + ontology / RDFValidation, inference, and cross-dataset identity become possible.
Whole-graph analytics as a featureNeo4j GDS, NetworkX, graph analytics platformPageRank, communities, and connected components are batch computations.
Transactional source of truth, high QPS, per-tenant ACLsNot this patternPlain markdown has no transactions or access control. Use a database / search service.
The rule of least infrastructure

Start with files, an index, and grep. Add search when finding pages becomes the bottleneck. Add a graph index when relationships become the bottleneck. Add a graph database when you need a transactional, permissioned, multi-user graph — not because the wiki has links.

7 · Graph health: orphans, hubs, bridges, drift

A graph gives you a vocabulary for wiki health. These are the metrics worth checking in lint:

MetricWhat it revealsAction
OrphansPages with no inbound links. They exist but are unreachable by navigation.Link them from a hub, merge them, or delete them.
Broken linksEdges to pages that do not exist. Sometimes a placeholder; sometimes drift.Create the page or fix the link. Do not ignore a growing list.
HubsHigh-degree pages. A hub can be a useful index or a gravity well that hides structure.Keep intentional hubs; split accidental supernodes.
BridgesPages that connect otherwise separate clusters. They are valuable and fragile.Protect them; add redundant links if a bridge is load-bearing.
Depth from indexHow many hops it takes to reach a page from index.md.Flatten navigation; add cluster hubs if depth grows.
Source coverageConcepts with no source pages, or sources with no concept links.Ingest more carefully; link evidence to claims.
Duplicate conceptsTwo pages for the same idea under different slugs.Merge and add aliases/redirects; update inbound links.
Stale edgesLinks to deprecated or superseded pages.Mark the target deprecated; update or remove the edge.

These checks can be deterministic. You do not need an LLM to count inbound links or resolve paths. The LLM is better at the semantic layer: "these two pages look like the same concept," "this link says supports but the source actually contradicts," "this hub is hiding three clusters." Use each tool for what it is good at.

8 · Questions a graph can answer

Here are the kinds of questions that become natural once the wiki is a graph. They are also a good test of whether you need a graph index at all: if you ask them weekly, add one; if you ask them once, write a script.

QuestionGraph operationWhy it matters
What links to this concept?Backlinks / reverse edgesFind context and evidence you forgot to look for.
How are these two ideas connected?Shortest pathExplain a relationship in one or two hops.
What is the load-bearing page?Degree / PageRank / centralityIdentify hubs worth reading first and protecting.
What clusters exist that nobody labeled?Community detectionDiscover themes and missing hubs.
What changed downstream of this source?k-hop traversal from the sourceImpact analysis when a source is corrected or superseded.
Which concepts have no evidence?Typed query: concepts without a source edgeFind claims that cannot be audited.
Which sources are orphaned?Sources with no inbound/outbound concept linksFind ingests that never became knowledge.
What is the shortest reading path?Path from index to a targetBuild onboarding or study guides from the graph.

For a small wiki, most of these can be answered with a 50-line script over parsed links. For a large or shared wiki, a graph index makes them interactive. The important thing is to ask the question before buying the engine.

9 · The interactive graph in this report

This report ships a small interactive graph as a demonstration. It is not generated from the HTML pages; it is a hand-built map of the report's pages, concepts, tools, and risks. Nodes are clickable, edges show relationships, and the side panel links back to the relevant section. Use it to see what a graph view feels like when the graph is small enough to read.

What the demo deliberately does not do

It does not parse markdown, run a layout server, or query a database. It is a static visualization with a tiny force simulation. That is the point: for a small wiki, the graph is a view, not a platform. If you want the real thing, point ki at a folder of markdown and query the index.

Five takeaways from Part 3
  1. The graph is already there. Files are nodes, links are edges, folders are containment.
  2. Backlinks are the killer feature. They turn a forward-only folder into a navigable network.
  3. Links are not relationships. Add typed edges only when the predicate does real work; always keep provenance.
  4. A graph view is not a query engine. Visualization helps humans; traversal and backlinks need an index or a script.
  5. Keep the files canonical. A graph index is a disposable cache, not a second source of truth.
