# PATTERN 10: KEYS AND CONSTRAINTS

Keys decide how rows are identified; constraints decide what data is allowed to exist. Together they are the part of a schema that cannot be reconstructed from application code — so they're worth getting right early.

## PRIMARY KEYS: SURROGATE vs NATURAL

A **natural key** is data that already identifies the row (an ISBN, an email, a country code). A **surrogate key** is a meaningless generated number or UUID.

| | Natural | Surrogate |
|---|---|---|
| Stability | Changes when the world changes | Never changes |
| FK size | As wide as the key | 4 or 8 bytes |
| Joins | Sometimes avoidable (the FK *is* the data) | Always required |
| Meaning leaked | Yes — the value is real data | No |
| Composite FKs | Often wide and awkward | Single column |

**Default to a surrogate key.** The decisive argument is that natural keys change, and a changing primary key means cascading updates across every referencing table. Values that look permanent usually aren't: email addresses change, ISBNs get reissued, country codes are retired (Yugoslavia's `YU`, and `CS` after it). Even a US Social Security Number is not unique in practice.

**But still declare the natural key as `UNIQUE`.** This is the part people skip. The surrogate key handles identity and references; the natural key is a real business rule and belongs in the schema:

```sql
create table countries (
    country_id int generated always as identity primary key,
    iso_code   char(2) not null unique,     -- the natural key, enforced
    name       text not null
);
```

The exception where a natural key wins outright is a **junction table**: `(student_id, course_id)` is already unique, immutable, and needed as an index. Adding a surrogate `id` there buys nothing (see `02_many_to_many.md`).

## `IDENTITY` vs `SERIAL`

```sql
-- Legacy
id serial primary key
id bigserial primary key

-- Standard, and what you should write in new code
id int generated always as identity primary key
id bigint generated always as identity primary key
```

`SERIAL` is not a real type — it's a macro that creates an `int` column, a sequence, and a default. That indirection causes three real problems:

- **Ownership and permissions are separate.** Granting `INSERT` on the table isn't enough; the role also needs `USAGE` on the sequence, which is a classic "works in dev, fails in prod" bug.
- **Nothing prevents manual inserts.** `INSERT INTO t (id) VALUES (5)` succeeds and does not advance the sequence, so the next generated id collides. `GENERATED ALWAYS` rejects this outright, requiring an explicit `OVERRIDING SYSTEM VALUE` to bypass.
- **`ALTER TABLE ... DROP DEFAULT`** silently orphans the sequence.

`GENERATED BY DEFAULT AS IDENTITY` is the middle ground — it permits manual values (useful for data imports and for ORMs that insist on supplying ids) while remaining a proper identity column.

**One property both share:** sequences are **not transactional**. A rolled-back insert consumes its id permanently. Gaps in an id column are normal and expected — never present a surrogate key to users as a count, and never assume `max(id)` equals the row count.

## UUID KEYS

Use a UUID when ids are exposed publicly, generated client-side, or must be unique across databases (multi-region, offline-first sync, merging shards).

```sql
create extension if not exists pgcrypto;

create table documents (
    id uuid primary key default gen_random_uuid(),  -- v4, random
    title text not null
);
```

**The cost, and it's real:** UUIDv4 is random, so inserts land at random positions in the B-tree. That means page splits, poor cache locality, and an index that is far larger than the equivalent `bigint` one (16 bytes vs 8, plus fragmentation). On a high-insert table the difference is measurable — often 2-3× slower inserts and a substantially bigger index.

**UUIDv7 fixes this.** It's time-ordered, so new rows append to the right edge of the index like a sequence does, while keeping global uniqueness and non-guessability. PostgreSQL 18 has a built-in `uuidv7()`; before that, use an extension (`pg_uuidv7`) or generate them in the application (the `uuid` npm package supports v7).

**A hybrid many teams use:** `bigint` identity as the primary key and internal FK target, plus a separate unique `uuid` (or a short random slug) as the public identifier. Small, fast joins internally; no enumerable ids externally.

```sql
create table orders (
    order_id     bigint generated always as identity primary key,
    public_id    uuid not null unique default gen_random_uuid(),
    ...
);
```

Sequential integer ids leak information — competitors can measure your growth rate by placing two orders a week apart — and invite enumeration attacks when authorization is weak. That's the reason to avoid exposing them, and it's independent of the key you use internally.

## THE CONSTRAINT TOOLKIT

Ordered roughly by how much work they save you.

### NOT NULL

The most underused constraint. Every nullable column is a branch every consumer must handle, and a question the schema doesn't answer ("does this mean unknown, or not applicable, or not yet?"). Default to `NOT NULL` and justify nullability, not the other way round.

Adding `NOT NULL` to an existing column scans the table. Since PG 12, adding a `NOT NULL` column *with* a default is instant.

### UNIQUE

```sql
-- Simple
email text not null unique,

-- Composite: unique per tenant, not globally
unique (tenant_id, email),

-- Partial: uniqueness only among live rows (soft delete)
create unique index uq_users_email_active on users (email) where deleted_at is null;

-- Case-insensitive
create unique index uq_users_email_lower on users (lower(email));
```

**NULLs are distinct in a UNIQUE constraint.** `UNIQUE (a, b)` allows `(1, NULL)` twice, because `NULL = NULL` is unknown, not true. This surprises people constantly. PostgreSQL 15+ can change it:

```sql
unique nulls not distinct (a, b)   -- now (1, NULL) can only appear once
```

### CHECK

Row-local invariants. Cheap, always enforced, and self-documenting.

```sql
price       numeric(10,2) not null check (price >= 0),
email       text check (email like '%@%'),
status      text not null check (status in ('draft', 'published')),
check (ends_at > starts_at),
check (num_nonnulls(post_id, video_id) = 1),   -- exactly one set
check (discount_pct between 0 and 100)
```

Limits worth knowing: a CHECK can only see **one row** (no subqueries, no aggregates), and it must be **immutable** — `check (starts_at > now())` is rejected, because a row valid at insert time would become invalid later and `pg_dump`/restore would fail.

Adding a CHECK to a large table locks it while every row is validated. Avoid that with a two-step:

```sql
alter table t add constraint c check (...) not valid;  -- instant, applies to new rows
alter table t validate constraint c;                   -- scans, but takes a weaker lock
```

### EXCLUSION CONSTRAINTS

The one most people don't know exists, and the only declarative way to say "no two rows may conflict" for something other than equality. Booking systems, scheduling, and effective-dated tables all need it.

```sql
create extension if not exists btree_gist;

create table room_bookings (
    booking_id int generated always as identity primary key,
    room_id    int not null,
    period     tstzrange not null,

    -- No two bookings for the same room may overlap in time
    exclude using gist (room_id with =, period with &&)
);
```

Without this you're doing a `SELECT` to check for conflicts and then an `INSERT` — a race condition that two concurrent requests will eventually hit, producing a double-booking that's very hard to reproduce afterwards. The constraint makes it impossible.

### FOREIGN KEYS

Covered in `01_one_to_many.md`. Three additions:

**Index them yourself** — PostgreSQL doesn't. Unindexed FKs make every parent delete scan the child table.

**`MATCH FULL` for composite FKs.** By default, a composite FK with *some* columns NULL passes without checking anything. `MATCH FULL` requires all-or-nothing:

```sql
foreign key (tenant_id, user_id) references users (tenant_id, user_id) match full
```

**FK checks are not free.** Every insert into the child takes a shared lock on the parent row. High-throughput inserts against a few hot parent rows will contend.

### DOMAINS

A reusable named type with constraints attached. Good for values that recur across many tables.

```sql
create domain email_address as text
    check (value ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');

create domain positive_money as numeric(12,2)
    check (value >= 0);

create table invoices (
    billing_email email_address not null,
    total         positive_money not null
);
```

The constraint is defined once and enforced everywhere the domain is used. The tradeoff is indirection — a reader has to look up what `email_address` permits — so reserve domains for genuinely repeated concepts.

## DEFERRABLE CONSTRAINTS

By default, constraints are checked after each statement. `DEFERRABLE INITIALLY DEFERRED` moves the check to `COMMIT`, which is what makes circular references and bulk reordering possible.

```sql
-- Swapping two unique values without a temporary placeholder
alter table items add constraint uq_position unique (list_id, position)
    deferrable initially deferred;

begin;
  update items set position = 2 where id = 1;  -- transiently duplicates
  update items set position = 1 where id = 2;
commit;  -- checked here, and passes
```

Only `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, and `EXCLUDE` can be deferred. **`CHECK` and `NOT NULL` cannot** — they are always immediate.

Note that a `DEFERRABLE` unique constraint cannot be used as an `ON CONFLICT` arbiter, so deferring by default has a real cost. Prefer `DEFERRABLE INITIALLY IMMEDIATE` and `SET CONSTRAINTS ... DEFERRED` in the specific transaction that needs it.

## WHY CONSTRAINTS, NOT APPLICATION VALIDATION

The common objection is that validating in the application gives better error messages and avoids a round trip. Both are true. Neither is the point.

Application validation protects **one code path**. The database is also written to by migrations, admin scripts, `psql` sessions, background jobs, data imports, a second service in another language, and whatever the on-call engineer types at 3am. A constraint is the only rule that holds for all of them.

Constraints also inform the **query planner** — a `NOT NULL` column lets it skip null checks, a `CHECK` can enable partition pruning, and a `UNIQUE` constraint tells it a join produces at most one row.

The right arrangement is both: validate in the application for good UX, constrain in the database for correctness. When they disagree, the database wins, which is the correct failure mode.

### COMMON MISTAKES

- **No unique constraint on the natural key** because "the surrogate key is the primary key." The business rule is now unenforced and duplicates will appear.
- **Using `SERIAL` in new code.** Prefer `GENERATED ALWAYS AS IDENTITY`.
- **UUIDv4 primary keys on a high-insert table** without knowing the index cost. Use v7.
- **Exposing sequential integer ids publicly.** Leaks volume, invites enumeration.
- **Assuming `UNIQUE` prevents duplicate NULLs.** It doesn't, unless you use `NULLS NOT DISTINCT`.
- **Check-then-insert instead of an exclusion constraint** for overlap rules. Races under concurrency.
- **Adding a CHECK or NOT NULL to a big table during peak traffic.** Use `NOT VALID` then `VALIDATE`.
- **Expecting gapless id sequences.** Rolled-back transactions consume ids. If you need gapless numbering (invoices, legal documents), that's a separate counter table with explicit locking — not a sequence.
- **Validating only in the ORM.** Every other writer bypasses it.

### KEY TAKEAWAYS

- Surrogate primary key + unique constraint on the natural key
- `GENERATED ALWAYS AS IDENTITY`, not `SERIAL`; `bigint` when in doubt
- UUIDv7 over v4 if you need UUIDs at all; consider `bigint` PK + public `uuid`
- `EXCLUDE USING gist` is the answer to "no overlapping bookings/periods"
- Constraints are the only validation that every writer is subject to
