pgvector: vectors like
ordinary columns.

pgvector is an extension, not a sidecar: vectors live in normal tables and inherit everything Postgres already does — ACID, joins, constraints, row-level security, WAL, replication, PITR, backup. This page is the strict engineering manual: what it guarantees, what it costs, and where its real ceilings are (pgvector 0.8.7, Postgres 13–18, October 2026).

1 · Status, licensing, guarantees

  • Current release: pgvector 0.8.7 (2026-10-01). Supports Postgres 13–18. Available from source, Docker (pgvector/pgvector:pg18), apt/yum, and effectively every managed Postgres (Supabase, Neon, RDS/Aurora, Azure, Cloud SQL, Timescale, Crunchy, Nile…).
  • License: PostgreSQL license (permissive OSS) — no field in a vendor contract stands between you and your vectors.
  • Full Postgres semantics: WAL-logged, so streaming replication, point-in-time recovery, pg_dump, and logical replication all just work on vector columns. Vectors participate in foreign keys, CHECK constraints, RLS policies, triggers, and joins.
  • Capacity: 32 TB per non-partitioned table is the storage ceiling; in practice RAM, recall, and vacuum behavior bind long before storage does.
  • Feature surface (0.8.x): exact + HNSW + IVFFlat search; vector / halfvec / bit / sparsevec types; L2, inner product, cosine, L1, Hamming, Jaccard; iterative index scans; binary/half-precision quantization via expression indexes; parallel builds; subvector indexing.

2 · Types and dimension limits

TypeElementStorageMax storedMax indexableUse for
vector(n)float324·n + 8 bytes16,000 dims2,000 dimsDefault dense embeddings (1536, 1024, 768).
halfvec(n)float162·n + 8 bytes16,000 dims4,000 dimsStorage/RAM halving; 3,072-dim models (OpenAI 3-large) that would otherwise fail to index.
bit(n)bitn/8 + 8 bytes1,048,560 dims (Postgres bit ceiling)64,000 dimsBinary quantization, perceptual hashes; Hamming/Jaccard metrics.
sparsevec(n)float32 (sparse)8·nonzero + 16 bytes16,000 nonzero1,000 nonzeroSPLADE-style learned-sparse embeddings.

Creating an HNSW index on a vector(3072) column is a hard error (column cannot have more than 2000 dimensions for hnsw index). The three legitimate answers: store as halfvec, index a quantized expression (binary_quantize(...)::bit), or reduce dimensions at the model level (Matryoshka-style output). A bare vector column (no dimension modifier) can even mix dimensions per row — useful when you version embedding models — but only same-dimension subsets can be indexed, via partial + expression indexes.

3 · Query shapes the planner will (and won't) index

-- The indexed shape: distance operator in ORDER BY, ASC, with LIMIT
SELECT id, content
FROM   documents
ORDER  BY embedding <=> '[0.1, -0.2, ...]'   -- cosine
LIMIT  10;

-- NOT indexed: any expression around the operator or DESC on similarity
SELECT id FROM documents
ORDER  BY 1 - (embedding <=> '[...]') DESC      -- planner falls back to a full scan
LIMIT 10;

Other shapes worth knowing (all from the official README):

-- "Neighbors of a row" (dedup / similar-items)
SELECT * FROM items
WHERE id != 1
ORDER BY embedding <-> (SELECT embedding FROM items WHERE id = 1)
LIMIT 5;

-- Distance threshold (combine with ORDER BY + LIMIT to use the index)
SELECT * FROM items WHERE embedding <-> '[3,1,2]' < 5;

-- Similarity score for display: cosine similarity = 1 - cosine distance
SELECT id, 1 - (embedding <=> '[...]'::vector) AS similarity FROM documents ...;

-- Aggregate helpers: AVG/sum work on vectors (useful for centroids, profiles)
SELECT category_id, AVG(embedding) FROM items GROUP BY category_id;
Index-not-used triage

If EXPLAIN (ANALYZE, BUFFERS) shows a sequential scan: confirm the indexed shape above; confirm an index with the matching opclass exists; on small tables a scan really is cheaper — let the planner be right. To force an index while debugging: BEGIN; SET LOCAL enable_seqscan = off; …. If a parallel scan looks too slow, the planner is ignoring TOASTed vectors; try ALTER COLUMN embedding SET STORAGE PLAIN (inline storage) for modest dimensions.

4 · HNSW vs IVFFlat: choosing and tuning

-- HNSW (the default recommendation): build-time knobs
CREATE INDEX CONCURRENTLY ON documents
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);        -- defaults; raise ef_construction for recall

-- Query-time dial (per session, or SET LOCAL per transaction)
SET hnsw.ef_search = 100;                      -- default 40; bigger = better recall, slower

-- IVFFlat (cheap builds, lower recall, needs data before build)
CREATE INDEX ON documents
  USING ivfflat (embedding vector_cosine_ops) WITH (lists = 1000);
SET  ivfflat.probes = 30;                      -- start near sqrt(lists)

Build accelerators: load data first, then index; raise maintenance_work_mem until the "graph no longer fits" NOTICE appears (and no further); raise max_parallel_maintenance_workers. In production use CREATE INDEX CONCURRENTLY. Track progress via pg_stat_progress_create_index. Remember: NULL vectors — and zero vectors under cosine — are not indexed at all.

5 · Filtered search: the honest problem and 0.8's fix

The single most-misunderstood behavior: with ANN indexes, Postgres applies the WHERE clause after the index scan. A filter matching 10% of rows with ef_search = 40 returns about 4 rows when you asked for 10. pgvector's own cost-estimation improvements (0.8) may steer selective queries to an exact plan — which is often better: 100% recall, B-tree pre-filtering.

-- Exact + B-tree is the correct first answer for selective filters
CREATE INDEX ON documents (tenant_id);
SELECT * FROM documents
WHERE tenant_id = 42
ORDER BY embedding <=> :q LIMIT 10;          -- exact kNN over the ~few hundred tenant rows

-- pgvector 0.8: iterative scans keep pulling candidates until LIMIT is satisfied
SET hnsw.iterative_scan = strict_order;        -- or relaxed_order (better recall, slight out-of-order)
SET hnsw.max_scan_tuples = 20000;              -- stop-loss; default 20 000
SET hnsw.scan_mem_multiplier = 2;              -- memory for the scan, multiple of work_mem
SELECT * FROM documents
WHERE status = 'published' AND lang = 'en'
ORDER BY embedding <=> :q LIMIT 10;

The decision ladder for WHERE + vector queries (Crunchy Data's framing, and the README's, agree):

  1. Filter matches a small slice (a tenant, "today's rows") → index the filter column(s); let Postgres do exact kNN on the slice. Deterministic, 100% recall.
  2. Stable, low-cardinality filter queried constantly (e.g. status = 'published') → partial HNSW index: … USING hnsw (embedding vector_cosine_ops) WHERE (status = 'published').
  3. Ad-hoc / compound filters → iterative scans (0.8), tune max_scan_tuples; fall back to oversample-then-filter: WITH nearest AS MATERIALIZED (… ORDER BY embedding <=> :q LIMIT :k*20) SELECT … FROM nearest WHERE … ORDER BY distance LIMIT :k.
  4. Many distinct filter values → partitioning (below).
Distance-predicate quirk

For WHERE distance < x style filters, put the vector search in a materialized CTE and apply the distance filter outside it (the README documents this executor behavior). On relaxed_order scans, order strictly with ORDER BY distance + 0 (the + 0 is needed on Postgres 17+) in an outer query.

6 · Multi-tenancy

pgvector's README is blunt: sharing one approximate index across tenants means one tenant's vectors occupy graph/cluster capacity and degrade everyone's recall and latency. The supported isolation tools are Postgres's own:

-- Isolation by partition (README pattern)
CREATE TABLE items (customer_id int, embedding vector(1536))
  PARTITION BY LIST (customer_id);
-- …or separate tables per tenant via your migration tool.
-- Security stays with RLS regardless of layout:
CREATE POLICY tenant_isolation ON documents
  USING (tenant_id = current_setting('app.tenant_id')::int);

RLS on a vector table works exactly like on any table — a genuine advantage over most dedicated vector stores, whose access control is coarser. Combine: partitions (performance isolation) + RLS (security isolation) + B-tree filtered exact search for small tenants.

7 · Hybrid search with Postgres full-text

One of pgvector's structural wins: the lexical side (the tsvector/GIN machinery in this repo's advanced_patterns/09_fulltext_search_geospatial.md) lives in the same table, so fusion is a query, not a pipeline between two systems. Reciprocal Rank Fusion combines rankings without reconciling incomparable scores:

WITH vec AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> :q) AS r
  FROM documents ORDER BY embedding <=> :q LIMIT 50
), lex AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(search_vector, q) DESC) AS r
  FROM documents, websearch_to_tsquery('english', :text) q
  WHERE search_vector @@ q LIMIT 50
)
SELECT d.id, COALESCE(1.0/(60+vec.r), 0) + COALESCE(1.0/(60+lex.r), 0) AS rrf
FROM vec FULL OUTER JOIN lex USING (id)
JOIN documents d USING (id)
ORDER BY rrf DESC
LIMIT 10;

(pgvector's official examples ship RRF and cross-encoder re-ranking patterns in Python.) Why bother: dense retrieval misses exact identifiers — SKUs, error codes, clause numbers, endpoint paths — while BM25/FTS misses paraphrase. 2026 practitioner consensus across Redis, Crunchy Data, and enterprise-RAG write-ups is that hybrid + re-rank is the production baseline; vendor material reports ~26–31% retrieval gains for hybrid over dense-only (treat as vendor/marketing grade, directionally consistent).

8 · Scaling ladder: quantization, DiskANN, sharding

Ordered by increasing operational commitment. Each rung buys roughly 2–30× working-set reduction or moves the hot set off the RAM assumption.

  1. Vertical scale + replicas. Postgres first: bigger box, hot standbys spread read load (WAL-replicated indexes), PgBouncer in front. Boring, and it defers everything else.
  2. halfvec tables and/or half-precision indexing. ~50% of bytes; raise the indexable-dimension ceiling to 4,000. 
    CREATE INDEX ON documents USING hnsw ((embedding::halfvec(1536)) halfvec_l2_ops);
  3. Binary quantization with re-ranking. 32× smaller index; oversample, then re-rank with the true vectors. 
    CREATE INDEX ON documents USING hnsw ((binary_quantize(embedding)::bit(1536)) bit_hamming_ops);

SELECT * FROM (
  SELECT * FROM documents
  ORDER BY binary_quantize(embedding)::bit(1536) <~> binary_quantize(:q) LIMIT 100
) half
ORDER BY embedding <=> :q LIMIT 10;
  4. Sharding on Postgres primitives. LIST partitions by tenant; Citus distributed tables (official pgvector example); connection-level routing with PgDog. Note ClickHouse's caution and Timescale's own: heavy UPDATE/DELETE churn bloats ANN graphs — batch and reuse.
  5. Disk-oriented indexes in-extension.
    • pgvectorscale (Timescale; Rust/pgrx; needs pgvector): StreamingDiskANN + SBQ — the index spans SSD, RAM holds compressed vectors; supports real-time inserts and get_next()-style streaming filtering. Vendor benchmark (50 M 768-dim Cohere vectors @99% recall): 28× lower p95 and 16× the throughput of Pinecone s1 at ~75% lower self-hosted cost. Availability on managed providers varies; verify before committing.
    • VectorChord (vchordrq): pre-filtering via bitmaps (filter applied inside the search), better defaults per an independent 2026 benchmark (94% recall @ ~23 ms vs DiskANN ~31 ms at 512-limit on SIFT-like data — single blog, single run). Built-in IVF rerank options.
    • pg_diskann (Microsoft): PQ-based DiskANN, mostly relevant on Azure Postgres flexible server.
    Practical thresholds pulled together from ClickHouse's 2026 guidance and practitioner posts: pgvector HNSW comfortably serves ≤ ~1–10 M vectors (fit the graph in RAM); quantization/partial indexes push that to ~10–50 M; DiskANN-family is the answer at 10 M+ when RAM is the constraint; below ~1 M, HNSW-vs-everything-else barely matters — tune ef_search first.
  6. Then — and only then — a dedicated system. See Part 4's short list of genuine triggers.

9 · Operations: builds, vacuum, upgrades, monitoring

Taskpgvector-specific practice
Upgrade extensionALTER EXTENSION vector UPDATE; after installing the new binaries; check SELECT extversion FROM pg_extension WHERE extname='vector';. ANN rebuilds can change results — re-run your recall harness.
Vacuum with HNSWFast path: REINDEX INDEX CONCURRENTLY idx; VACUUM tbl; — vacuum of big HNSW graphs is slow; reindexing first is the README's documented speedup. Heavy churn (re-embedding) = frequent versions of this dance, or partition-and-drop instead of delete.
BackupsEverything standard works (pg_dump, basebackup, PITR) — but dumps get large: 100 M × 1536-dim vectors ≈ 610 GB of data before indexes. Plan transfer and restore time accordingly.
Recall monitoringSampled A/B: run the query exact (SET LOCAL enable_indexscan = off;) and compare result sets in production traffic (pgvector README's own technique). Alert on recall drift after rebuilds/upgrades/data shifts.
Index size / bloatSELECT pg_size_pretty(pg_relation_size('idx')); tracked over time; growth without data growth = dead-tuple pressure.
Statement monitoringpg_stat_statements as usual; watch the kNN query's buffers — ANN scans should be index-dominated.
IVFFlat driftCentroids reflect insertion-time distribution. After major distribution changes, rebuild; symptoms are recall loss, not errors.

10 · A worked production schema

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE doc_chunks (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id     bigint        NOT NULL REFERENCES tenants(id),
    doc_id        text          NOT NULL,
    chunk         text          NOT NULL,
    token_count   int,
    lang          text          NOT NULL DEFAULT 'en',
    status        text          NOT NULL DEFAULT 'published',
    embedding_model text        NOT NULL,            -- model lock-in is a schema fact
    embedding     halfvec(1536) NOT NULL CHECK (vector_dims(embedding) = 1536),
    search_vector tsvector,                          -- lexical side, same table
    created_at    timestamptz NOT NULL DEFAULT now()
);

-- keep the tsvector in sync (or use a STORED generated column)
CREATE FUNCTION chunk_tsv() RETURNS trigger AS $$
BEGIN
  NEW.search_vector := setweight(to_tsvector('english', NEW.chunk), 'D');
  RETURN NEW;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER chunk_tsv_trigger BEFORE INSERT OR UPDATE ON doc_chunks
  FOR EACH ROW EXECUTE FUNCTION chunk_tsv();

-- retrieval indexes
CREATE INDEX ON doc_chunks (tenant_id);                        -- exact + filter for small tenants
CREATE INDEX ON doc_chunks USING gin (search_vector);          -- hybrid's lexical leg
CREATE INDEX ON doc_chunks USING hnsw (embedding halfvec_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- security: vector data is tenant data
CREATE POLICY chunk_access ON doc_chunks
  USING (tenant_id = current_setting('app.tenant_id')::bigint);
ALTER TABLE doc_chunks ENABLE ROW LEVEL SECURITY;

Query (filtered ANN with iterative scan + hybrid fusion omitted for brevity):

BEGIN;
SET LOCAL hnsw.ef_search = 80;
SET LOCAL hnsw.iterative_scan = relaxed_order;
SELECT id, chunk, 1 - (embedding <=> :query_embedding::halfvec(1536)) AS similarity
FROM   doc_chunks
WHERE  tenant_id = :tenant AND status = 'published'
ORDER  BY embedding <=> :query_embedding::halfvec(1536)
LIMIT  10;
COMMIT;

That is the whole system: one table, one index set, standard Postgres ops. The costs — vacuum behavior of HNSW, recall monitoring, re-embedding jobs — are real but ordinary database work.
