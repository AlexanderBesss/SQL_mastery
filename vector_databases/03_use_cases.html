Part 3 of 4 · Where vectors earn their keep

Eight use cases
that survive scrutiny.

Each entry states the signal that it's genuinely a vector problem, the Postgres implementation, the strict caveat, and the bail-out condition — the point at which the honest answer stops being "add vectors". Read the bail-outs as part of the use case.

The admission test — run every idea through it
  1. Can you name the real query? "Find the policy about vacation" is a meaning-shaped query; "all orders over $500" is not. If every query maps to typed columns and predicates, vectors add risk, not value.
  2. Can you build an evaluation set (queries + expected results)? If you can't measure relevance, you can't ship retrieval — you can only hope.
  3. Do you have an embedding model whose training objective matches your similarity ("paraphrase", "same topic", "same product", "same face")? Mismatched objective = confident nonsense.

All three yes → proceed. Any no → fix that first, or don't build this.

1 · Semantic search over documents, tickets, product copy

Signal: users search with questions and vocabulary that differs from your corpus; keyword search under-finds. What to embed: chunks (300–800 tokens) or whole short documents. Why it works: cosine neighborhoods capture paraphrase — "how do I take time off" finds the PTO policy that never says those words.

-- exact search first; add HNSW when measured too slow
SELECT id, title FROM docs
ORDER BY embedding <=> :q LIMIT 10;

Strict caveats: ship it hybrid (FTS leg for identifiers — Part 2 §7); chunking strategy matters more than index choice; embedding model upgrades are a full re-embedding batch job.

Bail-out: if your queries are mostly exact tokens (SKUs, error codes, clause numbers), Postgres FTS or pg_trgm alone will beat vector search — see Part 4 §2.

2 · RAG retrieval for LLM applications

Signal: an LLM must ground answers in your corpus; the prompt needs the right 5–15 chunks. Why vectors: the model's question phrasing rarely matches document phrasing. Implementation: the worked schema in Part 2 §10 — chunks, metadata, HNSW + GIN in one table, RRF fusion, optional cross-encoder re-rank in the app tier.

Hype check

RAG's failure modes are overwhelmingly retrieval-quality problems (bad chunks, bad fusion, no re-rank, no eval), not database problems. The 2026 contrarian literature ("why you shouldn't use vector databases for RAG") is mostly arguing against vector-only retrieval and against buying a dedicated vector DB for what is usually a few-million-vector workload. Both arguments land on this report's side of the ledger: hybrid retrieval, Postgres unless a Part 4 trigger says otherwise.

Bail-out: if the answer always sits in one typed field or a JOIN answers it, that's a query — generate SQL/tool calls, don't embed.

3 · Recommendations and "similar items"

Signal: "more like this" over catalog entities; no labels, no behavior log yet, or content-based similarity is the product. What to embed: item title+description (or image+text multimodal). Postgres recipe: neighbors-of-a-row in one statement:

SELECT id, title, 1 - (embedding <=> (SELECT embedding FROM items WHERE id = :id)) AS sim
FROM items WHERE id <> :id AND status = 'active'
ORDER BY embedding <=> (SELECT embedding FROM items WHERE id = :id)
LIMIT 12;

Strict caveats: content similarity ≠ taste; once you have behavioral data, co-occurrence/collaborative signals usually beat raw content embeddings — consider storing trained item embeddings instead of text embeddings. Deduplicate the catalog first: near-identical listings crowd out diversity (use case 4 is your prerequisite).

Bail-out: ranking is dominated by rules/inventory/margin — vectors at most generate a candidate set; the SQL after it decides.

4 · Near-duplicate detection and content dedup

Signal: ingesting from many feeds; contracts/case law with reused clauses; UGC needing "already asked / already posted" checks; image spam. Why vectors shine: paraphrase-level duplication defeats hashes and FTS but is exactly what cosine distance measures.

-- gate on insert: is this (near-)duplicate of something we have?
SELECT id, 1 - (embedding <=> :new_emb) AS similarity
FROM documents
ORDER BY embedding <=> :new_emb LIMIT 1;
-- application rule: similarity > 0.95 ⇒ flag/reject; 0.85–0.95 ⇒ human review

-- image perceptual hashes: binary vectors + Hamming distance, no ANN even needed at moderate scale
SELECT id FROM image_hashes ORDER BY phash <~> :new_hash LIMIT 5;

Strict caveats: distance thresholds must be set on your data, not copied from a blog; near-dup detection quality is a property of the embedding model. Threshold-based flags need an eval set with human labels, or you're calibrating blind.

Bail-out: exact re-posting (byte-identical) — a hash column with a B-tree is cheaper and exact.

5 · Candidate matching: résumés↔jobs, entities↔entities, products↔products

Signal: two free-text populations to pair up; hard filters first (location, date, price), fuzzy similarity last. Pattern: SQL enforces the contract, vectors score the vibe:

SELECT c.id, 1 - (c.embedding <=> j.embedding) AS fit
FROM candidates c
WHERE c.availability <= 30 AND c.relocated IS NOT TRUE   -- typed predicates do the real filtering
ORDER BY c.embedding <=> j.embedding                      -- vectors only order the survivors
LIMIT 25;

Strict caveats: this is the highest-harm use case on the list: embedding "similarity" encodes everything the model saw. For anything touching hiring, credit, housing — audit for protected-attribute proxies, keep the vector score advisory, and document the human decision path. Embedding models trained on generic text underperform on domain language (legal, medical, code): evaluate domain-appropriate models (e.g. legal-tuned embeddings measurably move CUAD-style scores in 2026 tests).

Bail-out: if matching rules are rule-expressible ("same tax ID", "same phone"), rules first, vectors never.

6 · Image / audio / multimodal retrieval

Signal: search a media library by concept ("outdoor portrait at dusk"), or find visually similar assets. Implementation: CLIP-family / multimodal embedding models put images and text in one vector space; store halfvec in Postgres beside the asset metadata; query with text or image embeddings identically.

Strict caveats: 2026's multimodal embedding-inversion research (IEEE TDSC) shows leaked CLIP embeddings can be reconstructed into recognizable private images with generative models — media embeddings are personal data in the GDPR sense when the media is. Granularity is coarse; expect "right concept, wrong photo" and design the UI around it.

Bail-out: classical CV needs (counting, detection, measurement) — that's not a similarity search; use a CV pipeline.

7 · Anomaly and drift monitoring over embedding spaces

Signal: "which incoming documents/transactions/users look unlike the corpus". Mean distance to k nearest neighbors is an outlier score; centroid drift over time slices is a distribution-drift alarm. Postgres does this with plain SQL + pgvector aggregates:

-- daily centroid drift: distance between yesterday's and today's embedding centroid
SELECT 1 - (AVG(embedding) FILTER (WHERE created_at >= now() - interval '1 day')
         <=> AVG(embedding) FILTER (WHERE created_at <  now() - interval '1 day')) AS drift
FROM documents;

Strict caveats: anomaly scores need labeled incidents to calibrate thresholds; drift alarms without a response plan are noise.

Bail-out: tabular anomaly detection (numeric distributions, segment counts) — statistical tools on the relational columns, not embeddings.

8 · Classification / triage by k-NN vote on labels

Signal: you have thousands of human-labeled items and want cheap triage of new ones (support tickets → queues, content → review category). Pattern: take the top-k neighbors of the new item's embedding and majority-vote their labels; label taxonomy changes don't require re-embedding — only labels change.

Strict caveats: minority classes are systematically outvoted (weight votes by distance or inverse class frequency); label drift poisons the "model"; for high-stakes classification a trained classifier with metrics beats vibes.

Bail-out: stable, well-populated classes and volume — train a real classifier; k-NN voting is bootstrap-era machinery, useful while labels are scarce.
