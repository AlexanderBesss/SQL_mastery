When a vector database
is the wrong tool.

The most expensive database decision of the 2020s has been buying a second stateful system to answer questions SQL could answer. This page draws the line: ten hard "don't" rules, the anti-pattern catalog, the privacy ledger, and — to stay honest — the short list of triggers where a dedicated vector database is genuinely the right call.

1 · Ten rules: do not use vector search when…

  1. …the query maps to typed columns and predicates. "Orders over $500 last week" is a WHERE clause. Vectors can only make this slower, fuzzier, and unauditable. If you can write it in SQL, write it in SQL.
  2. …exact identifiers carry the meaning. SKUs, error codes, API paths, contract clause numbers, drug names: dense retrieval blurs tokens that must not blur. Postgres FTS, pg_trgm, or a plain B-tree beats ANN here — and published practitioner numbers back it (one 2026 stress test: BM25 P95 6–9 ms vs HNSW P95 18–30 ms on the same corpus). Hybrid keeps vectors as a second signal, never the only one.
  3. …the corpus is small. Under roughly 100 k vectors, exact search is already milliseconds; adding an ANN index buys latency you don't need while silently spending recall. A few 2026 RAG tutorials run millions of documents' vectors from a numpy array — a database (vector or otherwise) isn't the hard part; retrieval quality is.
  4. …100% recall is a requirement. Completeness is a legal and medical necessity ("every document mentioning this clause"). ANN is approximate by construction; even tuned HNSW can miss true neighbors after rebuilds. Use exhaustive/lexical methods, or ANN only as a first pass you provably overfetch.
  5. …the system must be explainable and deterministic. Regulators, auditors, and incident reviews need "why this result". A cosine distance of 0.61 in a 1,536-dim space is not an explanation, and the answer can change under index tuning. Rules + lexical retrieval give you reproducible justifications.
  6. …you cannot build an evaluation set. If nobody can say which results are right, you cannot tune ef_search, choose a model, or prove the feature works. No eval → no vector feature. (This is a product-readiness rule, not a database rule — and it fails more often than any technical one.)
  7. …the vocabulary is controlled. Internal tools with a known synonym set: a thesaurus/synonym table + FTS is exact, maintainable, and debuggable. Embeddings pay continuous cost to solve a discrete problem.
  8. …the corpus churns wholesale and freshness is contractual. UPDATE in Postgres = DELETE + INSERT: heavy re-embedding churn bloats HNSW graphs, slows vacuum, and forces reindex cycles; ANN indexes in dedicated engines have their own compaction costs. If your pipeline rewrites the whole index hourly, fix the pipeline before choosing the store — and design for partition-and-swap instead of update-in-place.
  9. …the content is sensitive and unredacted, and you'd store vectors in a weaker trust zone than the text. See §3: embeddings reconstruct. Do not use a third-party vector service to hold "just the vectors" of confidential data on the theory that vectors are anonymous.
  10. …you don't yet have the problem. "We need AI search" before anyone has typed a query that keyword search failed. Every legitimate vector project starts from a named failure of lexical retrieval.

3 · The privacy ledger: embeddings are not obfuscated text

The security literature is settled on this point: text embeddings can be inverted back toward the original text. Milestones: Vec2Text and GEIA (2023) reconstructed sentences from same-model embeddings; the ACL 2024 Transferable Embedding Inversion Attack did it without access to the original model, using a surrogate, and showed it on a clinical dataset; 2026 work extended this to zero-training cross-domain inversion (Zero2Text) and to multimodal CLIP databases, where leaked embeddings were reconstructed into recognizable private images (IEEE TDSC). Consequences for architecture:

  • An embedding is subject to the same classification as its source text. "We only put vectors in the vendor's cloud" is not a privacy control — it is an attack surface with a hosted inversion target.
  • Deletion obligations (GDPR erasure, retention schedules) propagate to embedding columns, search indexes, replicas, and backups. Vectors are easy to forget in a "right to be forgotten" sweep because nobody thinks of them as text. Postgres helps here: the embedding row is the record row — one DELETE, one backup story.
  • Mitigations are partial: pre-embedding redaction of PII, access control at the embedding column (column grants/RLS), perturbation/DP approaches (research-grade, quality tradeoffs). Minimization is the real control: embed what you need, not everything.
Compliance rule

If the source text would require encryption-at-rest, access audit, and deletion propagation, the embedding column inherits all three duties. In a threat model, treat "database of embeddings" as "database of lightly-encoded text."

4 · When a dedicated vector database IS the right answer

Honesty requires the inverse list. Each trigger is checkable — if you can't point to one in writing, stay in Postgres:

  • Billions-scale retrieval with aggressive sharding (Milvus-class workloads; the 2026 comparisons consistently place Milvus/Zilliz in this lane, with K8s-native ops and GPU indexing — at real DevOps cost).
  • Sub-20 ms p99 at sustained high QPS on pure similarity search — dedicated engines optimize the single task; e.g. one 2026 roundup measured Qdrant p99 ≈ 12 ms at 10 M vectors vs Weaviate ≈ 16 ms, Milvus ≈ 18 ms (comparison-article numbers; re-measure).
  • Object-storage-native economics for huge corpora — Turbopuffer-style S3-backed architectures are the cheapest $/GB at large scale; no Postgres extension replicates that storage model.
  • Zero-ops managed retrieval as a product requirement — Pinecone's real value is not letting you own an index (serverless, autoscaling, enterprise compliance); you pay for it in unit-based pricing and a second system.
  • Native advanced retrieval pipelines as a package — Vespa-class hybrid + re-ranking + multi-stage ranking; Weaviate's built-in vectorizer/BM25 hybrid (and 2026's MCP server for agent access) genuinely compress app-tier work.
  • Hard architectural isolation between retrieval and the OLTP system — when a search spike must never touch the transactional database, a separate store is a firewall, not a redundancy.

5 · Postgres + search engine: the dual-store compromise

When §4 triggers are real but Postgres remains the source of truth, the standard 2026 pattern is dual-store: Postgres holds documents, ACLs, and lifecycle; the retrieval system holds derived indexes; sync is explicit (outbox pattern / logical decoding / the engine's connector), never best-effort dual writes. Budget for the costs you just bought: sync lag (stale results), schema drift, reconciliation jobs, and a re-index runbook. Test the boundary with a concrete question: what happens to retrieval correctness during a 10-minute sync outage? If the honest answer matters, Postgres-only (Part 2) was the right architecture.

6 · The decision tree, in words

  1. Is the query meaning-shaped (can't be written as predicates) and do you have an eval set? No → SQL / FTS / pg_trgm. Done. Most products stop here.
  2. Is the data already in Postgres (or comfortable living there)? No, and it won't move → go to the store your data is in; add vectors there (most 2026 engines have them).
  3. Corpus size: < ~100 k vectors → pgvector exact search, no ANN index. 100 k–10 M → pgvector + HNSW, tuned, hybrid leg, iterative scans. 10–50 M → pgvector + quantization / partitioning, or pgvectorscale / VectorChord. > ~50–100 M or any §4 trigger → dedicated engine as a derived index (dual-store), or as primary if the workload is retrieval-native.
  4. Any hard constraint that overrides the above? Determinism → ANN never owns the verdict. Privacy → trust boundary of the store must match the text's classification. Freshness → fix churn before storage choice.
  5. Whichever you pick: commit a recall/latency/cost target (e.g. "recall@10 ≥ 95%, p95 ≤ 80 ms, ≤ $X/1k queries") and re-measure at every upgrade. The number, not the brand, is the architecture.

7 · Sign-off checklists

Before writing the first vector query
  • Named lexical failure it fixes (a query users actually typed)
  • Evaluation set frozen (≥ a few hundred query→relevant judgments)
  • Embedding model chosen with a matching objective; re-embedding cost priced
  • Data classification done — embeddings inherit text's privacy class
  • Recall/latency/cost targets written down
Before production (pgvector)
  • Exact-search baseline measured; ANN added with a measured recall number
  • Indexable query shape verified in EXPLAIN; opclass matches the operator
  • Filter strategy chosen: B-tree exact / partial index / iterative scan / partition
  • Tenant isolation plan (partitions/tables + RLS) documented
  • embedding_model column + CHECK on dimensions exist
  • vacuum/REINDEX CONCURRENTLY cadence tested on a copy with realistic churn
  • Recall watchdog (exact-vs-ANN sampling) scheduled
  • Backup/restore rehearsed with vector columns (size-aware)
  • Upgrade path tested: ALTER EXTENSION vector UPDATE on staging + recall harness re-run
