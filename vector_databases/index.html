Vector databases,
without the hype.

What a vector database actually is, why PostgreSQL + pgvector is the right default for most real workloads, where the genuine limits are, and the specific conditions under which a dedicated vector database is the correct answer. Verdicts up front
  1. pgvector is the correct default for the majority of production vector workloads. If your data already lives in PostgreSQL and your corpus is up to roughly 5–10 million vectors, pgvector (0.8.x) with a tuned HNSW index is usually sufficient, and cheaper than operating a second stateful system.
  2. A vector index is an approximate-search trade, not magic. pgvector's default is exact search with 100% recall. Only add an ANN index (HNSW/IVFFlat) when brute force is measurably too slow — you then accept recall loss and tuning work.
  3. Production retrieval is hybrid: lexical (BM25/full-text) + semantic (vectors) + re-ranking. Vector-only retrieval reliably fails on exact identifiers — SKUs, error codes, contract clause numbers, API paths. Treat hybrid as the baseline, not an upgrade.
  4. Dedicated vector databases are justified by specific, checkable conditions — hundreds of millions of vectors, sub-20 ms p99 requirements, GPU indexing, hard isolation between tenants, or object-storage-backed cost tiers — not by the phrase "AI-powered".
  5. Embeddings are sensitive data. Published embedding-inversion attacks can reconstruct the original text. If the source text is personal or confidential, the embedding column is subject to the same access control, retention, and deletion duties.

Decision matrix — the whole investigation in one table

Your situationCorrect toolWhy
Data is in Postgres; corpus < ~5–10 M vectors; typical RAG/semantic-search latency budget (50–300 ms) Postgres + pgvector (HNSW) One system: joins, constraints, transactions, RLS, WAL, backups, replicas come free. Quantization (halfvec / binary) extends the headroom.
Corpus is small (< ~100 k vectors) Postgres + pgvector, exact search, no ANN index Brute force is already milliseconds and has 100% recall. Adding HNSW trades away recall you didn't need to give up.
Users type exact tokens: order numbers, SKUs, error codes, clause IDs Postgres full-text search (GIN) or pg_trgm — possibly with vectors as a second signal Lexical matching is exact, explainable, and faster (P95 single-digit ms in published practitioner tests). Vectors blur identifiers.
10–100 M vectors, already on Postgres, RAM-constrained pgvector + quantization, or pgvectorscale (StreamingDiskANN) / VectorChord Keep Postgres as source of truth; move the index away from "entire graph in RAM" assumptions.
Hundreds of millions–billions of vectors, sustained high QPS, sub-20 ms p99, or GPU indexing Dedicated vector DB (Milvus, Qdrant, Pinecone, Turbopuffer…) Purpose-built sharding, quantization-on-write, and index families that Postgres extensions do not cover.
Hard per-tenant isolation or independent scaling of retrieval from the OLTP system Dedicated vector DB, or Postgres with per-tenant tables/partitions + replicas Shared ANN indexes leak recall (and noisy-neighbor latency) across tenants.
Retrieval must be deterministic, auditable, explainable (regulatory lookup, legal discovery) SQL predicates + full-text search; ANN only as a helper, never the authority ANN is approximate by construction: the same query after an index rebuild can return different rows.
Corpus changes wholesale every day (re-embedding everything) Redesign ingestion first; then Postgres with batching, or a dedicated system UPDATE in Postgres is delete+insert: churn bloats HNSW graphs and makes vacuum/reindex a routine chore.

Reading benchmarks honestly

Vendor numbers quoted in this report are labeled. Example: Timescale's widely-cited claim that Postgres with pgvector + pgvectorscale beat Pinecone's storage-optimized index at 28× lower p95 latency and 75% lower cost was measured on 50 M 768-dim Cohere vectors at 99% recall, self-hosted on EC2 — it is a vendor benchmark at a scale chosen to favor the architecture. It is directionally useful evidence, not a universal constant. Any number you plan to deploy on should be re-measured on your vectors, your filters, and your recall target.
