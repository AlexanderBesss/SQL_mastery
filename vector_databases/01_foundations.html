What "vector search"
actually is.

Strip the branding and a vector database does one job: find the k items whose numeric fingerprints are closest to a query fingerprint, fast. Everything else — recall, filtering, cost, "AI" — follows from how that one job is implemented.

1 · Embeddings: where the numbers come from

An embedding model maps content (text, image, audio, code) to a point in a d-dimensional space such that similar content lands near each other. "Similar" is whatever the model was trained to mean — paraphrase, topic, click behavior, pixel layout. The model choice silently defines your product's definition of similarity; this is the single most consequential decision in the stack, and the database is downstream of it.

Strict rules about models
  • Never change embedding models without re-embedding the whole corpus. Vectors from two models are mutually meaningless; mixing them in one index silently poisons results.
  • Store the model identity with every vector (a column, not tribal knowledge). It makes versioned re-embeddings and side-by-side evaluation possible.
  • Dimension reduction is a real option. Several 2026 models ship with Matryoshka-style flexible dimensions; practitioners report tiny quality loss truncating 3,072-dim vectors to 256–512 (e.g. ~0.6% correlation decay on OpenAI 3-large in one Milvus test). Fewer dims = smaller index, faster distance math, and you clear pgvector's 2,000-dim limit.
  • MTEB leaderboard scores are a filter, not a verdict. Benchmarks measure public datasets; your corpus, your chunking, and your queries decide whether a model is good.

2 · Distance metrics and operators

"Closest" needs a definition. The metric must match the model card — the model was trained so that one specific geometry means similarity, and the others are approximations at best.

Metricpgvector operatorMeansUse when
Cosine distance<=>Angle between vectors; ignores magnitudeText embeddings; the model card says cosine. Most common.
Negative inner product<#>Dot product (negated because Postgres only scans indexes ASC)Vectors already normalized to length 1 (OpenAI, many others) — marginally faster than cosine.
L2 / Euclidean<->Straight-line distanceModel card says L2 (e.g. some image/self-hosted models).
L1 / taxicab<+>Sum of absolute differencesRare; pgvector 0.7+ supports it for ranking-like cases.
Hamming / Jaccard<~> / <%>Bit disagreement / set overlap (binary vectors)Binary hashes (image perceptual hashes, binary-quantized embeddings).

For normalized vectors cosine similarity = inner product, and cosine distance = 1 − similarity. pgvector's cosine index skips zero vectors and never indexes NULLs — know this before wondering why a row "disappeared" from results.

Opclass trap

Each index in pgvector is built for one metric (vector_cosine_ops, vector_l2_ops, vector_ip_ops…). The query's operator must match an existing index's opclass or the index is simply not used — there is no error, just a slow query. If you need two metrics, build two indexes and pay twice.

3 · Exact vs approximate nearest neighbor

Exact (brute-force) search compares the query against every vector. Perfect recall, embarrassingly parallel, and cheap at small scale: pgvector's default with no vector index is exact search. On modern hardware, scanning hundreds of thousands of 1,536-dim vectors takes tens to low hundreds of milliseconds — often fast enough for backfill jobs and low-QPS features.

Approximate nearest neighbor (ANN) indexes trade exactness for speed by searching a subset of the data structure. Three quantities trade against each other and you pick two (at best all three get worse):

  • Recall@k — the fraction of the true k nearest neighbors actually returned. "95% recall" means 1 in 20 of your top-10 results is wrong/missing.
  • Latency — time to return k results at a given recall.
  • Memory / index size — what must be resident for the index to be fast.
The order of operations
  1. Start with exact search. Measure it. (No vector index = guaranteed 100% recall.)
  2. Exact search slow, or QPS expensive? Add an ANN index and set an explicit recall target (e.g. 95–99%).
  3. Tune the recall/latency dial (ef_search / probes) against that target.
  4. Only then consider quantization or a different index family for scale.

Skipping step 1 is the most common way teams end up with "vector search feels off": they tuned latency without ever measuring the recall they gave away.

4 · Index families: HNSW, IVFFlat, DiskANN

FamilyIdeaStrengthsCostsIn Postgres
HNSW (graph) Multilayer "small-world" graph; greedy walk from entry points toward the query. Best speed/recall tradeoff; no training step; supports incremental inserts; battle-tested (also used inside Qdrant, Weaviate, Milvus). Largest memory footprint; slowest builds; the graph wants to be in RAM for best latency. pgvector 0.5+ (USING hnsw).
IVFFlat (clustering) k-means the corpus into lists; query searches only the probes nearest lists. Fast, small builds; simple model of behavior; useful when data arrives before you can tune. Lower speed/recall than HNSW; must be built after data exists (training step); recall degrades as the distribution drifts from the old centroids — plan re-builds. pgvector 0.1+ (USING ivfflat).
DiskANN / disk-oriented Graph laid out for SSDs; only compressed vectors (binary/quantized) stay hot in RAM, full vectors re-read from disk for re-ranking. Scales far beyond RAM with high recall; strong at tens–hundreds of millions of vectors. Newer/extra extension; needs fast NVMe; build behavior varies (early pgvectorscale builds were single-threaded; current versions offer parallel-build settings). pgvectorscale (Timescale, StreamingDiskANN + SBQ); pg_diskann (Microsoft, Azure-oriented); VectorChord's vchordrq (pre-filtering via bitmaps).
Inverted file + PQ / ScaNN-style IVF coarse routing + product-quantized residuals. Very compact indexes; high throughput. Not part of pgvector; appears in FAISS and dedicated engines. Not in pgvector (relevant if you compare vendors).

The dials, in one line each: HNSW builds with m (connections per node) and ef_construction (build-time candidate width) — bigger = better recall, slower builds, more memory; queries tune ef_search (search width per query, default 40). IVFFlat builds with lists and queries with probes. DiskANN-family equivalents are algorithm-specific but play the same role.

5 · Quantization: the scale lever

Quantization stores each vector with fewer bits, shrinking the index and the working set — at a recall cost that is recovered by re-ranking with the original vectors. In pgvector:

  • halfvec — 16-bit floats: half the bytes, index up to 4,000 dims. Nearly free precision loss; the standard choice for text-embedding-3-large (3,072 dims).
  • binary_quantize() → bit index — 32× smaller (1 bit/dim); the index only remembers each dimension's sign, so you fetch an oversampled candidate set and re-rank with the true vectors. Fast builds, small RAM at scale.
  • Subvector indexing (e.g. first 256 dims of a Matryoshka model) — index a prefix, re-rank full vectors.
  • Vendor variants: Timescale's SBQ (statistical binary quantization) inside StreamingDiskANN; PQ/SQ in dedicated engines.
Sizing intuition

vector(1536) = 4·1536+8 ≈ 6.1 KB/row. 1 M rows ≈ 6.1 GB of raw vectors, and an HNSW index adds graph links on top (rule of thumb: budget ≥ the raw vector size in RAM for the hot graph). The same corpus as halfvec(1536) halves that; binary-quantized it is ~190 MB before re-ranking data. These estimates decide "can it stay in RAM", which decides HNSW vs DiskANN-family vs quantized HNSW — see Part 2.

6 · Evaluation: recall is a product decision

You cannot tune what you do not measure. The minimum honest harness:

  1. Freeze a sample of real queries (or synthetic ones from real documents).
  2. Compute ground truth with exact search (pgvector default; parallel sequential scan).
  3. Run the ANN query at various ef_search/probes; compute recall@k = |ANN top-k ∩ exact top-k| / k.
  4. Plot recall vs p50/p95 latency; pick the operating point that meets the product requirement.
  5. Re-run this after every major data-model change, index rebuild, or pgvector upgrade.

For relevance quality (not just index fidelity), you need judgment: humans or a cross-encoder scoring query–document pairs. Index recall is necessary, never sufficient — perfect recall of a bad embedding space is still bad search.
